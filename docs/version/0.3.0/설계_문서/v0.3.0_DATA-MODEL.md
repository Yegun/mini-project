## 1. 무엇을 저장하고, 무엇을 저장하지 않는가

데이터는 PostgreSQL 의 **같은 DB 안에 표 7개**로 둔다. DB 를 따로 만들지 않는다. (✅ D-041) 클라우드 DB 는 **PostgreSQL 16.15** 이고 제공처는 "수파"다(Supabase 로 이해했고 확인이 필요하다). (✅ 사용자 선택, Q-22)

|---|---|---|---|
| 저장한다 — 계정 | `users` | 계정 한 개가 한 줄. 이메일과 비밀번호 해시 | ✅ ARCHITECTURE 4-2, D-046, D-094 |
| 저장한다 — 로그인 상태 | `sessions` | 기기 한 대의 로그인 상태가 한 줄. 마지막 사용 시각 | ✅ ARCHITECTURE 4-2, D-095 |

- 이름·단위는 글자 수 제한이 없고, 목록 개수에도 제한이 없다. (✅ D-025)
- 여유·주의·임박·지남은 칸이 없다. (✅ D-011)
- **DB 가 막는 규칙 (✅ 사용자 선택, Q-08)**: `quantity` > 0 / `purchase_date` ≤ `expiry_date` (✅ D-003) / `storage`·`source`·`status` 는 정해진 값만 (글자 + 허용 값 검사, ✅ Q-07) / 처리 상태와 처리한 날짜의 짝. 최종 판단은 API 가 하고(D-010) DB 는 마지막 안전장치다.
- **색인**(검색을 빠르게 하는 장치, ✅ Q-10): 홈 목록용 `user_id, status, expiry_date, purchase_date, name` / 기록 목록용 `user_id, status, processed_date`. 규칙표(30개)는 중복 불가 칸 외에는 만들지 않는다.
- 같은 식품을 두 기기에서 동시에 고치면 **마지막으로 저장한 것이 이긴다.** 버전 칸은 두지 않는다. (✅ Q-20)
- **이름순** 정렬(A1·C1·D2)은 **글자 코드 순으로 고정**한다. 한글은 가나다 순, 영문은 대문자가 소문자보다 앞이다. DB 의 기본 정렬 규칙을 따르지 않는다. (✅ 사용자 선택, Q-23)
- 날짜 계산의 "오늘"은 DB 시계(`CURRENT_DATE`, `now()`)가 아니라 API 의 `get_today()` 값을 넘겨서 쓴다. 클라우드 DB 의 시간대가 한국이 아닐 수 있어 DB 시계를 쓰면 한국 시간 0시 기준(D-088)과 어긋난다. (✅ D-087, D-088, API-SPEC 0절 · 🟡 DB 쪽에서의 적용) 이것은 **날짜** 이야기이고, 30분을 가리는 로그인 상태의 시각(`sessions.last_used_at`)은 따로 Q-13 에서 정한다.
- API 는 값이 DB 에 닿기 전에 먼저 검사한다. 수량 소수 셋째 자리(`invalid_quantity`), 날짜 모양(`invalid_date`), 번호 모양(`not_found`)이 모두 그렇다. DB 의 자료형은 잘못된 값을 오류로 막거나(날짜·UUID) 조용히 고쳐 저장하기(소수 반올림) 때문이다. (✅ API-SPEC 0절 입력 검사, 5절 14번)

## 3. 화면 표시 ↔ 저장 값

> 한 줄이 한 가지 값이다. 식품 값은 D-032 의 영어 이름이다. 규칙표의 화면 표시는 3-4절에 있다.

### 3-1. 고르는 값 (식품)

| 칸 | 화면에 보이는 것 | 저장 값 | 비고 |
|---|---|---|---|
| 보관 방법 | 상온 | `room` | 직접 등록은 3가지 모두 고를 수 있음. 규칙표 식품은 "불가"인 방법이 흐리게 보이고 고를 수 없다 (D-005) |
| 보관 방법 | 냉장 | `fridge` | 위와 같음 |
| 보관 방법 | 냉동 | `freezer` | 위와 같음 |
| 처리 상태 | (따로 보이지 않음. 홈 목록에 나오는 식품) | `none` | 홈 목록은 이 값인 식품만 보여 준다 (A1) |
| 처리 상태 | 다 먹음 → 홈에서 빠지고 기록 화면의 다 먹음 목록에 나옴 | `eaten` | |
| 처리 상태 | 버림 → 홈에서 빠지고 기록 화면의 버림 목록에 나옴 | `discarded` | |
| 등록 방식 | (따로 보이지 않음. 등록 화면이 A2 인지 A3 인지로 정해진다) | `rule` (규칙표에서 골라 등록) | 보관 방법·구매일·이름을 고칠 때 어떤 규칙을 쓸지 가른다 (D-029) |

### 3-3. 저장하지 않고 계산해서 보여 주는 값

| 화면에 보이는 것 | 저장 값 | 계산 방법 (API 가 한다) |
|---|---|---|
| 상태 색 **여유** | 없음 (계산) | 남은 날 6 이상 |
| 상태 색 **주의** | 없음 (계산) | 남은 날 3~5 |
| 상태 색 **임박** | 없음 (계산) | 남은 날 0~2 (기한 당일 포함) |
| 상태 색 **지남** | 없음 (계산) | 기한 다음 날부터 |
| 달력에서 숨김 | 없음 (계산) | 지난 지 4일 이상. 목록에는 남는다 |
| 달력의 "오늘" 세로선 | 없음 (계산) | API 가 목록 응답에 담아 주는 오늘 날짜 (D-021) |
| 홈 목록 순서 | 없음 (계산) | 기한 빠른 순 → 구매일 이른 순 → 이름순 (D-015) |
| 기록: 다 먹음 (올해 / 이번 달) | 없음 (계산) | `status` = `eaten` 이고 `processed_date` 가 올해 / 이번 달(서버 한국 시간)에 드는 내 식품 수 |
| 기록: 버림 (올해 / 이번 달) | 없음 (계산) | `status` = `discarded` 이고 같은 기준 |
| 기록: 현재 총 식품 종류 | 없음 (계산) | `status` = `none` 인 내 식품의 **이름 종류 수**. 글자가 완전히 같은 이름은 한 종류 (D-067, API-SPEC D1) |
| 기록: 보관 상태별 수 | 없음 (계산) | `status` = `none` 인 내 식품을 `storage` 별로 센 수 (D-068) |
| 기록: 식품 상태별 수 | 없음 (계산) | `status` = `none` 인 내 식품에 같은 판정을 써서 센 수. **달력에서 빠진 지난 지 4일 이상 식품도 지남에 센다** (D-069, API-SPEC 5절 13번) |
| 기록: 처리한 식품 목록 | 없음 (계산) | 내 식품 중 `eaten`/`discarded` 를 나눠, `processed_date` 가 최근인 순 → 같으면 이름순 (D-073, D-074, API-SPEC 5절 8번) |

- 남은 날 = 기한 − 오늘, 모든 식품에 같은 기준, 날(일) 단위. (✅ D-014)
- 화면은 이 값을 색으로 보여 주기만 하고 판정하지 않는다. 화면이 하는 날짜 계산은 막대를 이번 주 7일에 맞춰 자르는 것뿐이다. (✅ D-009, D-016)
- 삭제한 식품은 행이 없으므로 어떤 숫자에도 들어가지 않는다. (✅ D-070)

### 3-4. 규칙표 (검색 결과·등록 화면)

## 4. 계정과 로그인 상태

### 4-1. 계정 표 `users`

| 칸 | 영어 이름 | 자료형 | 뜻 | 누가 넣는지 | 필수 | 변경 규칙 | 근거 |
|---|---|---|---|---|---|---|---|
| 계정 번호 | `id` | UUID (DB 가 자동 생성, ✅ Q-04) | 계정 한 개를 구분하는 번호. `foods.user_id`, `sessions.user_id` 와 잇는다 | 시스템 | 필수. 기본키 | 바뀌지 않는다 | ✅ ARCHITECTURE 4-2 |
| 이메일 | `email` | TEXT | 계정을 구분하는 값. **같은 이메일로 두 번 가입할 수 없다.** 형식은 @ 와 점이 있는 모양까지만 검사한다 | 사용자 (가입 때) | 필수. **중복 불가** | 바꾸는 기능은 없다. **소문자로 통일해 저장**해서 대문자·소문자만 다른 이메일도 같은 이메일로 본다 (✅ 사용자 선택, Q-02). 앞뒤 공백도 지우고 저장한다 (✅ Q-06) | ✅ D-046, D-058, D-096 |
| 비밀번호 해시 | `password_hash` | TEXT | 비밀번호를 해시한 값. **사용자마다 다른 솔트가 이 값 안에 함께 들어 있다.** 원문은 저장하지 않는다 | 시스템 (가입 때) | 필수 | 바꾸는 기능은 없다 (비밀번호 변경 안 함, D-050) | ✅ D-094, 사용자 선택 (Q-11) |

- **`password_salt` 칸은 두지 않는다.** ARCHITECTURE 4-2 는 계정 표를 `id`, `email`, `password_hash`, `password_salt` 로 적었지만, 사용자가 "솔트가 해시에 들어 있는 방식"을 선택해서(Q-11) 칸이 하나 줄었다. 사용자마다 다른 솔트를 쓴다는 D-094 는 그대로 지켜진다. 알고리즘 이름은 구현 계획에서 정한다. ARCHITECTURE 의 칸 목록은 이에 맞게 고쳐야 한다.

- 이메일 형식·비밀번호 규칙(8자 이상, 영문·숫자·특수문자 모두 포함)은 **가입 때만** 검사한다. 로그인에서는 검사하지 않고 맞지 않으면 모두 `login_failed` 로 돌려준다. (✅ D-047, D-096, API-SPEC 5절 12번) 비밀번호 규칙은 원문을 볼 수 있는 때만 검사할 수 있어서 DB 에 거는 규칙이 아니다.
- 가입 시각 같은 기록용 칸은 두지 않는다. (✅ Q-19, 식품 표의 D-028 과 같은 취지)

### 4-2. 로그인 상태 표 `sessions`

| 칸 | 영어 이름 | 자료형 | 뜻 | 누가 넣는지 | 필수 | 변경 규칙 | 근거 |
|---|---|---|---|---|---|---|---|
| 로그인 상태 번호 | `id` | TEXT (✅ Q-12) | 한 기기의 로그인 상태를 구분하는 값. 브라우저의 쿠키 `session` 에는 긴 무작위 값이 담겨 요청마다 같이 오고, **DB 에는 그 값의 해시만 저장**한다 | 시스템 (가입·로그인 때, 무작위) | 필수. 기본키 | 바뀌지 않는다 | ✅ API-SPEC 0절, ARCHITECTURE 4-2. 사용자 선택 (Q-12) |
| 계정 | `user_id` | UUID | 이 로그인 상태가 어느 계정의 것인지 | 시스템 | 필수 | 바뀌지 않는다. 계정이 지워지면 이 줄도 따라 지워진다 (✅ Q-09) | ✅ ARCHITECTURE 4-2 |
| 마지막 사용 시각 | `last_used_at` | TIMESTAMPTZ (시간대 포함 시각, DB 시계 기준, ✅ Q-13) | 이 기기가 마지막으로 요청한 시각. **30분**이 지나면 로그인 상태가 끝난다 | 시스템. 🔒 요청이 성공할 때마다 갱신 | 필수 | 만료된 요청은 갱신하지 않는다 (끝난 로그인이 되살아나지 않게). 로그아웃하면 그 줄을 지운다 | ✅ D-052, D-053, D-095, API-SPEC 5절 15번 |

- 기기마다 `sessions` 에 한 줄씩 생긴다. 한 계정이 여러 기기에서 동시에 로그인할 수 있고, 한 기기의 로그아웃은 그 기기의 줄만 지운다. (✅ D-054, D-060)
- 이 표의 시각은 식품의 "날짜만 저장"(D-031)과 **다르다.** 30분 단위를 가려야 하므로 시각이 필요하다. 오늘 날짜를 정하는 `get_today()` 와 별개다. (✅ Q-13)
- 만료된 줄은 **만료된 요청을 거절할 때 그 줄을 지우고**, 로그인할 때 그 계정의 만료된 줄도 같이 지운다. 별도 정리 작업은 없다. (✅ Q-14)

## 5. 규칙표 (읽기 전용)

규칙표는 같은 DB 안의 **표 세 개**다. (✅ D-034, D-041) 식품 표는 규칙표 내용을 복사해 두지 않고, 필요할 때 API 가 읽는다.

**규칙표 전체에 같은 규칙**

| 항목 | 내용 | 근거 |
|---|---|---|
| 누가 넣는지 | 개발자만. 내용(30개 식품의 기본 보관 방법·가능 여부·최대 보관 일수·별칭)은 사용자가 식약처 기준 정식값으로 채웠다 | ✅ D-007, D-018, ARCHITECTURE 4-3 |
| 앱·API | 읽기만 한다. 앱 안에서 고치는 화면·창구는 없다 | ✅ D-007, API-SPEC 4절 |
| 계정 | 계정마다 나누지 않는다. **모든 계정이 같은 것**을 읽고, 개발자가 업데이트하면 모든 계정에 같은 새 내용이 적용된다 | ✅ D-062, D-093 |
| 읽기 전용을 지키는 방법 | **읽기 전용 DB 계정을 따로 만든다.** 앱(API)이 쓰는 DB 계정은 규칙표 세 표를 읽기만 할 수 있고, 개발자가 규칙표를 고칠 때는 별도 계정을 쓴다 | ✅ 사용자 선택, Q-16 |

### 5-1. 식품 `rules` (식품 한 줄, 30개)

| 칸 | 자료형 | 뜻 | 필수 | 변경 규칙 |
|---|---|---|---|---|
| `id` | UUID (**이름에서 계산한 번호**, Q-04 의 예외) | 규칙표 식품 한 건을 구분하는 번호. 이름에서 계산하므로 규칙표를 다시 채워도 번호가 같다(`seed_rules.py` 방식). 별칭·보관 방법별 정보와 잇는다 | 필수. 기본키 | 개발자만 |
| `name` | TEXT | 규칙표에 있는 식품 이름. 검색(C1), 등록(A2), 이름 수정(A5)에서 "규칙표에 있는 이름인지" 판단에 쓴다 | 필수. **중복 불가** | 개발자만 |
| `default_storage` | TEXT (`room` / `fridge` / `freezer`) | 등록 화면에서 미리 선택되는 보관 방법 | 필수 | 개발자만. 반드시 `rule_storage.allowed` 가 참인 방법이어야 한다 (규칙표를 채우는 작업의 검사로 지킨다. `seed_rules.py` 가 이미 한다, ✅ Q-15) |

### 5-2. 별칭 `rule_aliases` (식품 하나에 여러 개 가능)

| 칸 | 자료형 | 뜻 | 필수 | 변경 규칙 |
|---|---|---|---|---|
| `rule_id` | `rules.id` 와 같음 | 어느 식품의 별칭인지 | 필수 | 개발자만 |
| `alias` | TEXT | 같은 식품의 다른 이름. 검색에서 이름과 함께 찾는다 | 필수. **중복 불가** | 개발자만. 별칭이 없는 식품도 있을 수 있다 (줄이 없으면 됨) |

- 별칭은 다른 식품의 이름과 같으면 안 된다. DB 가 막지 않고 규칙표를 채우는 작업이 검사한다. (✅ Q-15)

### 5-3. 보관 방법별 정보 `rule_storage` (식품 하나당 상온·냉장·냉동 3줄)

| 칸 | 자료형 | 뜻 | 필수 | 변경 규칙 |
|---|---|---|---|---|
| `rule_id` | `rules.id` 와 같음 | 어느 식품의 정보인지 | 필수 | 개발자만 |
| `storage` | TEXT (`room` / `fridge` / `freezer`) | 보관 방법. 식품 표와 같은 값을 쓴다 (D-032). `rule_id` + `storage` 가 한 쌍으로 중복 불가 | 필수 | 개발자만 |
| `allowed` | 참 / 거짓 (BOOLEAN) | 이 방법을 고를 수 있는지. 거짓이 "불가"이고 A2·A3·A6 에서 흐리게 보이며 API 도 거절한다 (D-005) | 필수 | 개발자만 |
| `max_days` | 정수 (일 단위) | 이 방법으로 보관할 수 있는 최대 기간. A2 기한 계산과 A6 새 기한 계산(D-006)에 쓴다 | `allowed` 가 참일 때만 필수 (0보다 큰 정수). 거짓이면 비운다 | 개발자만 |

  - 과일(6): 사과, 바나나, 딸기, 귤, 포도, 배
  - 육류(3): 돼지고기, 소고기, 닭고기
  - 수산(4): 고등어, 오징어, 새우, 연어
  - 그 밖(4): 달걀, 우유, 두부, 콩나물
- 규칙표 값을 고치면 **이미 등록된 규칙표 식품(`source` = `rule`, `status` = `none`)의 기한도 같이 다시 계산해 저장**한다. 새 기한 = 구매일 + 새 `max_days`. 직접 등록(`manual`)·처리된 식품은 그대로 둔다. 상태 색은 저장하지 않고 기한으로 계산하므로 기한이 바뀌면 자동으로 따라 바뀐다. A6 은 실행하는 순간의 규칙표 값으로 계산한다. (✅ ARCHITECTURE 4-3, 사용자 확인 Q-26)
- 보관 방법을 바꾼 적 있는 식품은 이 재계산으로 기한이 구매일 + 새 `max_days` 로 되돌아갈 수 있다. 이력을 저장하지 않기 때문이다(D-024). 사용자가 "문서대로 재계산"으로 확인했다. (Q-26)
- 규칙표의 값(이름·기한 숫자 등)은 사용자가 채운 별도 작업물이다. 이 문서는 표 구조만 정하고 값은 적지 않는다. (✅ D-018)

| 창구 | 읽는 표 | 쓰는 표 | 조건 · 동작 |
|---|---|---|---|
| B1 가입 | `users`, `legacy_migration` | `users`, `sessions`, (첫 가입이면) `legacy_migration`, `foods` | 이메일을 소문자로 바꿔 `users.email` 중복 확인. 새 줄 + 이 기기의 `sessions` 줄. `legacy_migration` 에 줄이 없으면 첫 가입이다 (7절). 응답 `{email}` 은 저장된 소문자 이메일 🟡 |
| B2 로그인 | `users`, `legacy_migration` | `sessions`, (미완료 옮김이면) `foods` | 입력한 이메일도 소문자로 바꿔 찾는다. 해시가 맞으면 이 기기의 `sessions` 줄을 **새로** 만든다(다른 기기 줄은 그대로). 이메일 모양·비밀번호 규칙은 검사하지 않는다 |

**식품 한 건 (API-SPEC 0-1절)** — 식품을 돌려주는 창구(A1, A2, A3, A4, A5, A6, A7, D3)가 모두 쓴다.

| 응답 칸 | 저장 칸 · 계산 | 변환 |
|---|---|---|
| `id` | `foods.id` | 글자 36자 |
| `name` | `foods.name` | 그대로 |
| `storage` | `foods.storage` | 그대로 (`room`/`fridge`/`freezer`) |
| `quantity` | `foods.quantity` | NUMERIC → JSON 숫자, 소수 둘째 자리까지 🟡 |
| `unit` | `foods.unit` | 그대로 |
| `purchase_date` | `foods.purchase_date` | DATE → `YYYY-MM-DD` 글자 |
| `expiry_date` | `foods.expiry_date` | DATE → `YYYY-MM-DD` 글자 |
| `source` | `foods.source` | 그대로 |
| `status` | `foods.status` | 그대로 |
| `processed_date` | `foods.processed_date` | DATE → 글자. 비어 있으면 `null` |
| `expiry_status` | 저장 안 함. `expiry_date` − `get_today()` 로 판정 | `status` 가 `none` 이 아니면 `null` |
| `days_left` | 저장 안 함. `expiry_date` − `get_today()` (날짜끼리 뺀 정수) | 지났으면 음수. `status` 가 `none` 이 아니면 `null` |
| `show_on_calendar` | 저장 안 함. 지난 지 4일 이상이면 거짓 | `status` 가 `none` 이 아니면 `null` |
| (응답에 **없음**) | `foods.user_id` | 주인 번호는 응답에 내보내지 않는다. API-SPEC 0-1절에 칸이 없다 |

| 창구 · 응답 | 저장 칸 · 계산 |

| D1 `eaten.year`·`month`, `discarded.year`·`month` | `foods` 중 `status` 가 `eaten`/`discarded` 이고 `processed_date` 가 올해·이번 달인 줄 수 |

### 6-5. 오류 이유 ↔ 데이터의 상황

API-SPEC 3절의 이유 중 **데이터를 읽어야 정해지는 것**만 적었다. 나머지(`required`, `invalid_*`, `expiry_input_invalid`, `weak_password`)는 값 모양만 보고 정해지므로 DB 를 읽기 전에 API 가 판단한다.

| `reason` | 데이터에서 보이는 상황 |
|---|---|
| `login_failed` | `users` 에 그 이메일이 없거나 해시가 맞지 않음. 어느 쪽인지 구분하지 않는다 |
| `login_required` | 쿠키가 없거나, `sessions` 에 그 번호의 줄이 없거나, `last_used_at` 이 30분보다 오래됨 |
| `email_taken` | `users.email` 에 같은(소문자) 이메일이 이미 있음. **동시에 두 번 가입**해서 중복 방지 규칙(UNIQUE)에 걸린 경우도 이 이유로 돌려준다 🟡 |
| `not_found` | 내 식품 조건(번호 + `user_id` + `status`)에 맞는 줄이 없음. 번호 모양이 틀린 경우도 같다 — 번호를 UUID 전용 형태로 두면(Q-04) DB 에 보내기 전에 API 가 모양을 먼저 확인해야 한다 |
| `expiry_required` (409) | 실패가 아니라 "기한을 다시 적어 달라"는 응답. A5: 새 이름이 규칙표에 없는데 `expiry_date` 를 안 보냄. A6: `source` = `manual` 인 식품의 보관 방법을 **다른 것으로** 바꾸는데 `expiry_date` 를 안 보냄. 이때는 아무것도 저장하지 않는다 |
| `rule_not_found` | 이름·별칭이 `rules.name`·`rule_aliases.alias` 어디에도 없음 (A2). 규칙표 식품인데 이름이 `rules.name` 에서 사라짐 (A6) |
| `rule_name_exists` | 직접 등록의 이름이 `rules.name` 또는 `rule_aliases.alias` 와 같음 (A3) |
| `storage_not_allowed` | `rule_storage.allowed` 가 거짓인 방법 (A2, A6). A5 에서 식품의 이름을 규칙표 이름으로 바꿀 때 이미 저장된 `storage` 가 그 식품에서 "불가"인 경우도 같다 (✅ Q-24①, API-SPEC A5 에 더해야 함) |
| `storage_change_not_allowed` | 이미 지난 식품의 새 기한이 음수이거나 `get_today()` 보다 뒤가 되지 않음 (A6) |
| `expiry_in_past`, `purchase_after_expiry`, `rename_expired_not_allowed` | `get_today()`, `purchase_date`, `expiry_date` 의 날짜 비교 (2절 DB 안전 규칙과 겹침, Q-08) |

## 7. 기존 식품(v0.2.0) 옮기기

> 옮기는 방법의 세부는 구현 계획에서 정한다. 여기서는 **데이터가 어떻게 놓이는지**만 적는다. (✅ ARCHITECTURE 9절의 9번)

| 항목 | 내용 | 근거 |
|---|---|---|
| 언제 | 처음 가입하는 계정이 만들어지는 순간 자동으로 **한 번만**. 이후 가입하는 계정은 빈 상태로 시작 | ✅ D-042, D-043, D-044 |
| 누구 것 | 처음 가입한 계정. 의도하지 않은 사람의 계정이어도 이번에는 그대로 둔다 (배포 전) | ✅ D-043, D-099 |
| 무엇을 | v0.2.0 SQLite 의 식품 표 → `foods`. 규칙표도 PostgreSQL 의 `rules`·`rule_aliases`·`rule_storage` 로 옮긴다 | ✅ ARCHITECTURE 4-4, D-041 |
| 기록 | `legacy_migration` 에 첫 계정과 옮김 여부를 적는다 (아래) | 🟡 사용자 선택 (작은 표 하나) |
| 실패하면 | 복사는 전부 취소해 일부만 옮겨진 채 남지 않는다. 계정은 그대로 둔다. 첫 계정이 다음에 로그인할 때 성공할 때까지 다시 시도한다 | ✅ D-097 |
| SQLite 파일 | 옮긴 뒤에도 지우지 않고 백업으로 남긴다. 앱은 다시 읽지도 쓰지도 않는다 | ✅ D-038, D-098 |

### 7-1. 옮김 기록 표 `legacy_migration` 🟡

| 칸 | 자료형 | 뜻 | 필수 | 규칙 |
|---|---|---|---|---|
| `id` | 정수 | 항상 1. 이 표에는 **한 줄만** 있다 | 필수. 기본키 | 1 만 허용해 두 줄이 생기지 않게 한다. 두 사람이 동시에 처음 가입해도 한 줄만 만들어진다 |
| `user_id` | UUID | 옮겨 받는 계정(첫 계정) | 계정이 살아 있는 동안 필수. 계정이 지워지면 **이 칸만 비워지고 줄은 남아** "옮김이 끝났다"는 기록을 유지한다 (✅ Q-09) | `users.id` 와 같다 |
| `migrated` | 참 / 거짓 (BOOLEAN) | 옮김이 끝났는지 | 필수. 처음에는 거짓 | 옮김이 **성공한 묶음 안에서만** 참으로 바뀐다. 한 번 참이 되면 바뀌지 않는다 |

- **줄이 없다** = 아직 아무도 가입하지 않았다. 첫 가입이 이 줄을 만든다. **줄이 있다** = 첫 계정이 이미 정해졌고, 이후 가입하는 계정은 이 줄과 상관없이 빈 상태로 시작한다. (✅ D-042, D-044)
- 로그인할 때 `migrated` 가 거짓이고 `user_id` 가 로그인한 계정이면 옮김을 다시 시도한다. (✅ D-097)
- 표 이름·칸 이름은 이 문서가 제안했고 사용자가 확인했다. (✅ Q-18)

### 7-2. 칸 대응

| v0.2.0 SQLite 식품 칸 | v0.3.0 `foods` 칸 | 옮길 때 값 |
|---|---|---|
| `id` | `id` | 기존 번호를 **그대로 쓴다** (✅ Q-17) |
| (없음) | `user_id` | **첫 계정의 번호** (✅ D-043) |
| `name`, `storage`, `quantity`, `unit`, `purchase_date`, `expiry_date`, `source` | 같은 이름 | 그대로. 날짜 글자는 DATE 로 바뀐다 |
| `status` | `status` | 그대로 |
| (없음) | `processed_date` | `none` 이면 **비움.** `eaten`/`discarded` 이면 **옮기는 날(서버 한국 시간 오늘)** (✅ D-045, PRD US-013) |

### 7-3. 묶음(트랜잭션)의 경계 🟡

API-SPEC 0절의 "요청 하나가 한 묶음"은 식품 등록처럼 **정보 하나라도 유효하지 않으면 전부 저장하지 않는다**는 뜻이다 (✅ 사용자 확인, Q-25). B1·B2 의 "옮기다 실패해도 가입·로그인은 성공"은 D-097 이 따로 정했다. 아래는 이를 DB 묶음으로 나눈 것이다.

| 묶음 | 들어 있는 것 | 실패하면 |
|---|---|---|
| ① 가입 (B1) | `users` 줄 + `sessions` 줄 + (첫 가입이면) `legacy_migration` 줄 (`migrated` = 거짓) | 전부 취소. 가입 실패 (API-SPEC B1 의 500) |
| ② 옮김 | `foods` 줄 복사 전부 + `legacy_migration.migrated` = 참 | **②만** 취소. ① 은 그대로 → 가입은 201 로 성공하고 `migrated` 는 거짓으로 남는다 |
| 로그인 (B2) | `sessions` 줄 | 전부 취소. 로그인 실패 |
| 로그인 중 다시 옮김 | ② 와 같다 | ② 만 취소. 로그인은 200 으로 성공 |

- ② 는 `foods` 줄과 `migrated` = 참을 **같은 묶음에서** 바꾼다. 그래서 "일부만 옮겨진 채" 남거나 "옮겼는데 거짓으로 남는" 일이 없다. (✅ D-097)
- 다시 옮길 때 `legacy_migration` 줄을 잠가서, 두 기기에서 동시에 로그인해도 두 번 옮기지 않는다.
- 옮길 식품이 하나도 없으면(SQLite 파일이 없거나 비어 있음) ② 는 곧바로 `migrated` = 참으로 끝난다.
- 이 경계는 API-SPEC 0절과 어긋나지 않는다. (✅ Q-25)

## 9. 변경점

이전(v0.2.0)과 달라진 점만 모았다. 본문(1~8절)은 이번 버전의 내용이다.

| 항목 | 원 내용 (v0.2.0) | 변경점 | 근거 |
|---|---|---|---|
| 저장소 | SQLite. 이 컴퓨터의 파일 | PostgreSQL. 클라우드 DB. 기기에 DB 를 만들지 않는다 | D-038, D-039 |
