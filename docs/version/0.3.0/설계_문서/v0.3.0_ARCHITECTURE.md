# ARCHITECTURE — 냉장고 관리 웹 앱

> 근거: [prd.md](../기초문서/v0.3.0_PRD.md) v0.3.0 + 네 범주(화면·API·저장소·공통 검증) 분해. 결정 이력은 [DECISIONS.md](../기초문서/v0.3.0_DECISIONS.md) (D-번호), 질문 답변은 PRD 7절 (OQ-번호). 코드에 이미 정해져 있는 것은 코드를 근거로 했다.
> 표시: ✅ 확정 / 🟡 제안(승인 필요) / ⚠️ 아직 모름. 근거 US-ID 를 붙였다.
> 사용 기술은 **화면 React · API FastAPI · 저장소 PostgreSQL 세 가지뿐**이다. SQLite 는 폐기한다 (D-038). 그 밖의 도구 이름은 아직 정하지 않았다.
> 이 문서의 1~9절은 **이번 버전에서 쓰는 내용**만 적었다. 이전과 달라진 점은 **10절**에 모았다.

## 1. 전체 그림

```
 [브라우저: 화면(React)]  ──요청──▶  [API(FastAPI)]  ──읽기/쓰기──▶  [PostgreSQL(클라우드)]
        ▲                               │                            ├─ 계정
        │                               │                            ├─ 식품 (계정마다)
        │                               └─읽기만──▶                  └─ 규칙표(30개, 모두 공통)
        └──────────── 응답 ─────────────┘
```

- ✅ 데이터는 **클라우드 DB** 에 있다. 앱을 켤 때마다 기기에 DB 를 만들지 않고, 어느 기기에서 같은 계정으로 열어도 같은 식품이 보인다. (D-038, D-039)
- ✅ **로그인해야** 쓸 수 있다. 식품은 계정마다 따로다. (D-059, D-061)
- ✅ 배포는 이번 범위가 아니다. 오프라인 사용은 범위 밖이다. (D-040)
- 화면은 저장소에 직접 닿지 않는다. **저장소와 규칙표는 API만 만진다.**
- ✅ "오늘 날짜"는 **서버 시계, 한국 시간**으로 통일한다. 날짜는 한국 시간 0시에 바뀐다. (D-087, D-088) 코드에서 오늘은 `get_today()` 한 곳에서만 정한다. 한국 시간으로 바꾸는 곳도 이 한 곳이다.

| 처리 중 버튼 잠금 | 저장·등록·수정·삭제·다 먹음·버림·되돌리기·가입·로그인 버튼은 처리가 끝날 때까지 다시 누를 수 없다. 연타해도 요청은 한 번만 간다. 끝나거나 실패하면 다시 누를 수 있게 돌아온다 | OQ-48, D-100 |

- ✅ 홈의 **달력 막대나 목록의 식품을 누르면 식품 상세**로 간다. 상세에서 저장·처리·삭제가 성공하면 홈으로 돌아온다. (화면 코드 `FoodBarRow`·`FoodList`·`App.tsx`, D-020)
- 입력 화면에서 하는 검사(빈 값, 수량 0 이하, 비밀번호 규칙 등)는 **미리 알려 주는 용도**이고, 최종 판단은 API가 한다. (D-010)
- ✅ 앱을 켜거나 로그인한 직후 가장 먼저 **홈**이 보인다. 하위 화면(식품 상세 등)에서 뒤로 가면 **바로 전에 보던 화면**(홈 또는 기록)으로 간다. (D-081, D-085)
- ✅ 설정 화면·온보딩 화면은 만들지 않는다 (Later). 계정 탈퇴 버튼은 설정 화면에 둔다. (D-089, D-090)

## 3. API (FastAPI)

🔒 는 로그인한 계정만 부를 수 있다는 뜻이다 (D-059). 주소에는 `/api` 를 붙이지 않고, 화면의 개발 서버가 `/api` 를 떼고 API 로 넘겨 준다.
| 창구 | 주소 | 하는 일 | 근거 |
|---|---|---|---|
| 가입 | `POST /auth/signup` | 이메일·비밀번호 검사 → 계정 만들기. 첫 가입이면 기존 식품을 이 계정으로 옮긴다 | US-012, D-042, D-043, D-047, D-058 |
| 로그인 | `POST /auth/login` | 이메일·비밀번호 확인 → 로그인 상태를 만든다. 틀리면 어느 쪽인지 알리지 않는다 | US-012, D-057 |
| 로그아웃 🔒 | `POST /auth/logout` | 이 기기의 로그인 상태만 끝낸다. 다른 기기는 유지 | US-012, D-054, D-060 |
| 규칙표 검색 🔒 | `GET /rules?q=이름` | 이름이나 별칭에 검색어가 들어 있으면 찾는다(오타 보정 없음). 결과는 이름·기본 보관 방법·고를 수 없는 보관 방법. 빈 검색어는 빈 목록 | US-001, D-035 |
| 식품 목록 🔒 | `GET /foods` | **내** 식품 중 처리 상태가 "없음"인 것을 오늘 날짜(`today`)와 함께 돌려준다. 식품마다 상태·남은 날·달력에 보일지가 붙는다. 정렬은 기한 → 구매일 → 이름 | US-007, US-008, US-011, D-015, D-021, D-061 |
| 식품 한 건 보기 🔒 | `GET /foods/{id}` | 상세 화면용 (내 식품만) | US-004, US-005, D-063 |
| 식품 등록 (규칙표) 🔒 | `POST /foods` | 보내는 칸: `name`, `quantity`, `unit`, `purchase_date`, `storage`. 검사 → 구매일 + 방법별 기간으로 기한 계산 → 내 식품으로 저장 | US-001, D-061 |
| 식품 등록 (직접) 🔒 | `POST /foods/manual` | 위 칸 + `expiry_date`(날짜) 또는 `expiry_in_days`(며칠 뒤) 중 하나. 직접 적은 기한 그대로 내 식품으로만 저장, 규칙표에는 더하지 않는다 | US-003, D-092 |
| 식품 수정 🔒 | `PATCH /foods/{id}` | 보낸 칸만 바꾼다: `name`, `quantity`, `unit`, `purchase_date`, `expiry_date`(기한 다시 적기 때만) | US-004 |
| 보관 방법 변경 🔒 | `PATCH /foods/{id}/storage` | `storage`, `expiry_date`(직접 등록 식품일 때만). 비율 이어받아 기한 다시 계산 | US-005 |
| 처리 🔒 | `PATCH /foods/{id}/process` | `status` = `eaten` 또는 `discarded`. 처리 상태를 바꾸고 **처리한 날짜(서버 한국 시간 오늘)를 저장**한다. 행은 남긴다 | US-011, D-064 |
| 삭제 🔒 | `DELETE /foods/{id}` | 완전히 지움 (기록에도 안 남음). 성공하면 본문 없는 204 | US-006, D-070 |
| 기록 숫자 🔒 | `GET /records/summary` | 내 식품만으로 다섯 가지 숫자를 센다. 다 먹음·버림은 올해/이번 달(처리한 날짜 기준), 나머지는 지금 있는 식품 기준 | US-013, D-044 |
| 처리한 식품 목록 🔒 | `GET /records/foods` | 내 식품 중 다 먹음·버림인 것을 전체, 최근 처리한 순, 둘로 나눠 돌려준다 | US-013, US-015, D-073, D-074 |
| 홈으로 되돌리기 🔒 | `PATCH /foods/{id}/restore` | 처리 상태를 "없음"으로, 처리한 날짜는 지움. 나머지 값은 그대로 | US-015, D-072, D-075~D-077 |
| 살아 있는지 확인 | `GET /health` | `{"status": "ok"}` | — |

공통 약속

| 항목 | 내용 | 근거 |
|---|---|---|
| 식품 한 건의 응답 칸 | 저장된 칸 `id`, `name`, `storage`, `quantity`, `unit`, `purchase_date`, `expiry_date`, `source`, `status` + 계산해서 붙이는 칸 `expiry_status`, `days_left`, `show_on_calendar`. 처리된 식품은 계산 칸 세 개가 `null`. `expiry_status` 값은 `fresh`(여유) / `warning`(주의) / `soon`(임박) / `expired`(지남). 날짜는 `YYYY-MM-DD` 글자. 처리한 날짜 칸은 `processed_date` | D-009, D-032 |
| 오류 모양 | 항상 세 칸 `field`(문제가 된 칸, 없으면 `null`), `reason`(이유 이름), `message`(쉬운 문구). 상태 번호는 입력 오류 **422**, 없는 식품 **404**, 기한 다시 적기 **409**, 저장·불러오기 실패 **500**. 문구는 코드 한 곳에서만 고친다 (예: `not_found` → "찾을 수 없는 식품이에요."). 로그인 관련 오류는 아래와 같다. 로그인 실패 `login_failed` **401** "이메일 또는 비밀번호가 맞지 않아요." / 이미 가입된 이메일 `email_taken` **409** "이미 가입된 이메일이에요." / 로그인 필요·30분 만료 `login_required` **401** "다시 로그인해 주세요." / 비밀번호 규칙 위반 `weak_password` **422** (`field` = `password`) "비밀번호는 8자 이상이고 영문·숫자·특수문자를 모두 넣어 주세요." | D-008, OQ-03 |
| 기한 다시 적기 | 실패가 아니라 정해진 응답 하나. **409 + `reason` = `expiry_required`**, `field` = `expiry_date`. 화면이 알아보고 입력칸을 연다 | US-004, US-005 |
| 요청 단위 | 요청 하나가 한 묶음(트랜잭션). 중간에 실패하면 전부 되돌려 아무것도 바뀌지 않는다 | OQ-04 |
| 남의 식품 | 다른 계정의 식품 번호로 요청이 와도 없는 식품과 똑같이 오류만 돌려준다. 그 식품이 있는지 알려 주지 않는다 | D-063 |
| 로그인 확인 | 🔒 창구가 같은 한 곳에서 로그인 확인과 "내 식품만" 걸러 내기를 한다. 창구마다 따로 만들지 않는다 | D-061 |

## 4. 저장소

### 4-1. PostgreSQL — 식품 (계정마다)

| 정보 | 설명 | 근거 |
|---|---|---|
| 식품 번호 | 건마다 따로 구분 (같은 식품을 여러 번 사도 따로 둠). 시스템이 만드는 무작위 고유번호(UUID) | PRD 4-1, D-030, D-033 |
| 주인(계정) | 식품은 등록한 계정의 것. 모든 조회·수정·삭제·처리·집계가 이 값으로 걸러진다 | US-012, D-061 |
| 이름 | 비면 안 됨 | US-001, US-004 |
| 수량 / 단위 | 수량은 0보다 큰 숫자(소수 둘째 자리까지), 단위는 글자 | US-001, US-004, D-027 |
| 구매일 | 기본 오늘, 미래 가능 | US-001, US-004 |
| 보관 방법 | 상온 / 냉장 / 냉동 | US-005 |
| 권장 기한 | 날짜로 저장 | US-001, US-003 |
| 등록 방식 | 규칙표 / 직접. 직접 적은 기한은 구매일을 고쳐도 안 바뀌게 하고, 이름·보관 방법 변경 때 다시 계산하는 방법을 가른다 | US-003, US-004, US-005, D-029 |
| 처리 상태 | 없음 / 다먹음 / 버림 | US-011 |
| 처리한 날짜 | 다 먹음·버림으로 처리한 날짜. 시각은 저장하지 않는다. 되돌리면 지운다. 기록의 올해·이번 달 숫자가 이 값으로 센다 | US-013, US-015, D-064, D-066, D-075 |

- ✅ **여유·주의·임박·지남은 저장하지 않는다.** 기한과 오늘 날짜로 그때그때 계산한다. 저장하면 날짜가 지나도 안 바뀌어서 틀린다. (D-011)
- 삭제는 행을 완전히 지운다. 다먹음·버림은 행을 남긴다. 삭제한 식품은 기록에도 없고 되돌릴 수 없다. (US-006, US-011, D-013, D-078)
- ✅ 식품 표의 칸 이름·값·자료형은 D-032 로 정해져 있다. `id`(UUID 36자) / `name` / `storage`(`room`·`fridge`·`freezer`) / `quantity`(0보다 큰 숫자) / `unit` / `purchase_date`·`expiry_date`(`YYYY-MM-DD`, 구매일 ≤ 기한) / `source`(`rule`·`manual`) / `status`(`none`·`eaten`·`discarded`). 화면 목록용으로 `status, expiry_date, purchase_date, name` 순 색인이 있다.
- ✅ 식품 표에는 **주인 칸 `user_id`**(계정 표 `id` 와 같은 값)와 **처리한 날짜 칸 `processed_date`**(`YYYY-MM-DD`, 날짜만)가 더해진다. 처리하지 않았거나 되돌린 식품은 `processed_date` 가 비어 있다. (D-061, D-064, D-075)
- ✅ 만든 시각·고친 시각 칸은 두지 않는다. (D-028)
- ✅ 직접 등록한 식품은 등록한 계정의 식품 한 건으로만 저장된다. 규칙표에는 더해지지 않고 다른 계정에서는 보이거나 검색되지 않는다. (D-092)

### 4-2. PostgreSQL — 계정

| 정보 | 설명 | 근거 |
|---|---|---|
| 이메일 | 계정을 구분하는 값. 같은 이메일로 두 번 가입할 수 없다. 형식은 @ 와 점이 있는 모양까지만 검사한다 | US-012, D-046, D-058, D-096 |
| 비밀번호 | 8자 이상, 영문·숫자·특수문자 모두 포함해야 한다. **원문으로 저장하지 않고, 사용자마다 다른 솔트를 붙여 해시로 저장한다** | US-012, D-047, D-094 |
| 로그인 상태 | 기기마다 따로 만들어진다. 한 계정이 여러 기기에서 동시에 로그인할 수 있다. **마지막으로 쓴 뒤 30분**이 지나면 끝난다 | US-012, D-052~D-054 |

- ✅ 로그인 상태는 **서버가 기억한다.** 기기마다 따로 만들고, 요청할 때마다 마지막 사용 시각을 갱신해 30분이 지나면 그 기기의 로그인 상태를 끝낸다. (D-095)
- ✅ 계정 표는 `users`(`id` 고유번호, `email`, `password_hash` — 사용자마다 다른 솔트가 해시 값 안에 함께 들어 있다)이고, 로그인 상태 표는 `sessions`(`id`, `user_id`, `last_used_at` 마지막 사용 시각)이다. 기기마다 `sessions` 에 한 줄씩 생긴다.
- ✅ 가입 때 이메일 인증, 로그인 틀림 횟수 제한, 비밀번호 찾기·변경, 소셜 로그인은 만들지 않는다. (D-048~D-051)
- ✅ 회원 탈퇴는 이번에 만들지 않는다 (Later, R-023). 나중에 만들면 계정과 식품을 모두 지운다. (D-089, D-090)

### 4-3. PostgreSQL — 규칙표 (읽기 전용)

| 항목 | 내용 | 근거 |
|---|---|---|
| 크기 | 가장 많이 쓰는 신선식품 30개 | PRD 4-3, D-018 |
| 담는 것 | 이름, 별칭, 보관 방법별 권장 기한, 기본 보관 방법, 선택 불가 보관 방법 | PRD 4-3, D-034 |
| 관리 | 개발자가 DB 에서만 고친다. 앱 안에서 고치지 못한다 | D-007 |
| 읽는 곳 | API만 읽는다 | — |
| 쓰는 사람 | **모든 계정이 같은 규칙표**를 읽는다. 개발자가 업데이트하면 모든 계정에 같은 새 내용이 적용된다. 계정마다 복사본을 두지 않는다 | D-041, D-062, D-093 |

- ✅ 규칙표는 표 **세 개**다 (D-034). `rules`(`id` UUID 36자, `name` 중복 불가, `default_storage`) / `rule_aliases`(`rule_id`, `alias` 중복 불가, 식품 하나에 여러 개 가능) / `rule_storage`(`rule_id`, `storage`, `allowed` 0·1, `max_days`). 고를 수 있는 방법(`allowed` = 1)이면 `max_days` 는 0보다 큰 정수여야 하고, 고를 수 없으면 비운다. 기본 보관 방법은 반드시 고를 수 있는 방법이어야 한다.
- ✅ 개발자가 규칙표를 고치면 이미 등록된 규칙표 식품(`source` = `rule`, `status` = `none`)의 기한도 다시 계산한다. 직접 등록·처리된 식품은 그대로다.
- ✅ 규칙표도 PostgreSQL 에 둔다. 식품·계정과 **같은 DB 안에 표만 따로** 두고, DB 를 따로 만들지 않는다. (D-041)
- ✅ 기한 값을 포함한 규칙표 내용(기본 보관 방법, 가능 여부, 최대 보관 일수, 별칭)은 사용자가 식약처 기준 정식값으로 채웠다. (D-018, D-036 폐기)

### 4-4. 기존 식품 옮기기

- ✅ 로그인이 없을 때 쓰던 기존 식품은 **처음 가입하는 계정이 만들어지는 순간 자동으로 한 번만** 그 계정으로 옮긴다. 이후 가입하는 계정은 빈 상태로 시작한다. (D-042, D-043, D-044)
- ✅ 이미 다 먹음·버림으로 처리한 기존 식품은 처리한 날짜가 없으므로 **옮기는 날을 처리한 날**로 센다. (D-045)
- ✅ **SQLite 는 폐기한다.** 옮기고 난 뒤 앱은 SQLite 를 다시 읽지도 쓰지도 않는다. 식품 표뿐 아니라 규칙표도 PostgreSQL 로 옮긴다. (D-038, D-041)
- ✅ 옮기다 실패하면 복사는 전부 취소해 일부만 옮겨진 채 남지 않게 하고, 계정은 그대로 둔다. 첫 계정이 다음에 로그인할 때 성공할 때까지 다시 시도한다. (D-097)
- ✅ 옮긴 뒤에도 SQLite 파일은 지우지 않고 백업으로 남긴다. (D-098)
- ✅ 첫 가입이 의도하지 않은 사람의 계정이어도 이번에는 그대로 둔다. 배포할 때 다시 정한다. (D-099)

## 7. 데이터 흐름

(Task Flow 양식의 "Task 등록"은 이 앱에서 **식품 등록**을 뜻한다.)

### 7-1. 식품 등록 (규칙표 식품, US-001)

1. 화면: 이름 입력 → API 규칙표 검색 → 후보 표시
2. 화면: 하나 고르면 기본 보관 방법이 미리 선택됨, 사용자가 수량·단위·구매일(·보관 방법) 입력
3. 화면: V-01~03 미리 검사 → 등록 요청
4. API: **로그인 확인 (V-19)**, V-01~04 최종 검사
5. API: V-08 로 기한 계산 → V-07 확인
6. API → PostgreSQL: 저장 (**주인 = 내 계정**, 직접 적은 기한 = 아니오, 등록 방식 = 규칙표, 처리 상태 = 없음)
7. API → 화면: 저장된 식품과 상태 반환
8. 화면: 홈으로 돌아가 막대 표시

직접 등록(US-003)은 4~5가 V-05·V-06·V-07 로 바뀌고, 6에서 "직접 적은 기한 = 예, 등록 방식 = 직접"으로 **내 계정의 식품으로만** 저장한다 (규칙표에는 더하지 않음, D-092).

### 7-2. 상태 변경: 다 먹음 / 버림 (US-011)

1. 화면: 상세에서 '다 먹음' 또는 '버림' 누름
2. API: 로그인 확인, **내 식품인지**, 이미 처리되지 않았는지 확인 (V-14, V-18)
3. API → PostgreSQL: 처리 상태를 다먹음 또는 버림으로 바꾸고 **처리한 날짜(서버 한국 시간 오늘)를 저장** (행은 남김)
4. API → 화면: 성공
5. 화면: 홈으로 이동. 식품 목록에서 빠짐. 마지막 식품이면 빈 홈 안내

### 7-3. 홈 보기 (US-007, US-008)

1. 화면 → API: 식품 목록 요청
2. API: 로그인 확인 → PostgreSQL 에서 **내 식품 중** 처리 상태가 "없음"인 식품 읽기
3. API: 각 식품에 V-12 상태 판정(서버 한국 시간 오늘)과 "달력에 보일지"를 붙이고 임박순(같으면 구매일 이른 순)으로 정렬
4. API → 화면: 목록 + 오늘 날짜 (D-021)
5. 화면: "달력에 보일지"가 예인 식품만 V-13 으로 이번 주에 맞춰 막대를 자르고 상태 색을 입힘.

### 7-4. 수정 · 보관 방법 변경 (US-004, US-005)

1. 화면: 수정 요청
2. API: 로그인 확인, 내 식품인지(V-18), V-01~03 · V-07 · V-04 검사
3. API: 무엇이 바뀌었는지에 따라
   - 구매일: 직접 적은 기한이 아니면 다시 계산, 맞으면 그대로
   - 이름: 규칙표에 있으면 V-09 로 다시 계산(직접 등록이어도 규칙표로 전환), 없으면 "기한을 다시 적어야 함" 응답
   - 보관 방법: 규칙표 식품이면 V-09 · V-10 으로 다시 계산, 직접 등록이면 "기한을 다시 적어야 함" 응답
   - 수량·단위: 기한과 상태 그대로
4. 화면: "기한을 다시 적어야 함"이면 입력칸을 열고, 새 기한은 V-05 로 검사해 다시 요청
5. API → PostgreSQL 저장 → 화면에 막대와 색 갱신

### 7-5. 삭제 (US-006)

1. 화면: 확인 창에서 확인해야 요청
2. API: 로그인 확인, 내 식품인지(V-18) → PostgreSQL 에서 행을 완전히 지움 (기록에도 안 남음)
3. 화면: 홈으로 이동. 마지막 식품이면 빈 홈 안내

### 7-6. 가입 · 로그인 · 로그아웃 (US-012)

가입
1. 화면: 이메일·비밀번호 입력 → V-15 미리 검사 → 가입 요청
2. API: V-15, V-16 최종 검사
3. API → PostgreSQL: 계정 저장. **첫 계정이면 기존 식품을 이 계정으로 옮긴다** (7-10)
4. API → 화면: 로그인된 상태로 **홈**이 보임 (D-081)

로그인
1. 화면: 이메일·비밀번호 입력 → 로그인 요청
2. API: 계정 확인. 틀리면 어느 쪽인지 알리지 않고 실패 (V-17)
3. API: 이 기기의 로그인 상태를 만든다 (다른 기기와 별개, D-054)
4. 화면: **홈**으로 감 (이미 로그인된 상태로 앱을 켜도 홈)

로그아웃·만료
1. 로그아웃: 이 기기의 로그인 상태만 끝내고 로그인 화면으로 간다
2. 30분 만료: 마지막으로 쓴 뒤 30분이 지나 요청하면 V-19 로 거절 → 화면이 로그인 화면으로 보냄. **입력 중이던 내용은 사라진다** (D-055). 다시 로그인하면 홈 (D-056)

### 7-7. 기록 보기 (US-013)

1. 화면: 기록 탭 → API 기록 숫자 요청
2. API: 로그인 확인 → **내 식품만**으로 다섯 숫자를 센다 (V-22)
   - 다 먹음·버림: 처리한 날짜가 올해/이번 달(서버 한국 시간)에 드는 건수
   - 현재 총 식품 종류: 처리 상태가 "없음"인 식품의 이름 종류 수
   - 보관 상태별: 같은 식품을 상온/냉장/냉동으로
   - 식품 상태별: V-12 판정을 그대로 써서 여유/주의/임박/지남으로
3. API → 화면: 숫자. 화면은 상태 색만 입힌다 (D-009)
4. 화면: 모두 0 이면 0 + 안내 문구 + 등록 버튼 (D-071)

### 7-8. 홈으로 되돌리기 (US-015)

1. 화면: 기록 화면의 처리한 식품 목록(다 먹음/버림 나눔)에서 하나를 골라 '홈으로 되돌리기'
2. API: 로그인 확인, 내 식품인지, 처리된 식품인지 확인 (V-18, V-20)
3. API → PostgreSQL: 처리 상태 = 없음, 처리한 날짜 지움. 나머지 값 그대로 (V-21)
4. API → 화면: 성공
5. 화면: 목록에서 빠지고 숫자 갱신. 홈에서는 다시 보임(기한이 지났으면 지남)

### 7-9. 탭 이동 (US-016)

1. 화면: 홈 또는 기록 탭을 누름
2. 화면: 같은 탭이면 아무 일도 없음
3. 화면: 식품 등록·수정 화면에서 **입력한 것이 있으면** 확인 창. 확인하면 이동하고 입력 사라짐, 취소하면 남음. 입력한 것이 없으면 바로 이동
4. 화면 → API: 이동할 화면에 필요한 데이터 요청. 실패하면 쉬운 오류 메시지, 지금 화면 유지, 같은 탭을 다시 눌러 재시도

### 7-10. 기존 식품 옮기기 (US-012, US-014)

1. API: 첫 계정이 만들어지는 순간 한 번만 실행 (D-042)
2. API: 기존 SQLite 의 식품을 읽어 PostgreSQL 에 **그 계정의 식품으로** 저장 (D-043)
3. API: 이미 처리된 식품(다 먹음·버림)은 처리한 날짜를 **옮기는 날**로 채움 (D-045)
4. 이후 가입하는 계정은 빈 상태 (D-044)
- ✅ 중간에 실패하면 복사는 전부 취소하고 계정은 그대로 둔다. 첫 계정이 다음에 로그인할 때 성공할 때까지 다시 시도한다 (D-097). 옮긴 뒤 SQLite 파일은 백업으로 남긴다 (D-098).
