# API-SPEC — 냉장고 관리 웹 앱 API 약속

> 근거: PRD · ARCHITECTURE · DECISIONS · USER-WORKFLOW · SCREEN-SPEC
> 이 문서는 화면에서 사용자가 무언가를 눌렀을 때 화면과 API 가 주고받는 것을 적은 것이다. 사용자 행동 하나에 창구 하나다.
> 주소·메서드·보내는 칸·오류 이름 중 **ARCHITECTURE 3절에 이미 정해진 것은 그대로 따랐다.** 기준 문서에 없던 칸 이름·이유 이름·성공 상태 번호·세부 동작은 5절에 모았고, 사용자가 정한 것과 이 문서에서 정한 것(확인 필요)을 구분해 적었다.
> 문서에 없고 정하지도 않은 내용은 4절 "하지 말 것"에서 확인할 수 있다.

| 표시 | 뜻 |
|---|---|
| ✅ | 기준 문서에 근거가 있거나 사용자가 정한 **확정** |
| 🔒 | 로그인한 계정만 부를 수 있는 창구 (D-059) |

## 0. 모든 API 에 같은 약속

| 항목 | 약속 | 근거 |
|---|---|---|
| 주소 | `/api` 를 붙이지 않는다. 화면의 개발 서버가 `/api` 를 떼고 API 로 넘겨 준다 | ✅ ARCHITECTURE 3절 |
| 로그인 상태 | 쿠키로 보낸다. 가입·로그인 응답이 쿠키를 심고, 브라우저가 이후 요청마다 알아서 같이 보낸다. 서버가 로그인 상태를 기억하고 🔒 요청마다 마지막 사용 시각을 갱신해, 마지막 사용 뒤 30분이 지나면 그 기기의 로그인 상태를 끝낸다. 쿠키 이름은 `session`, 자바스크립트에서 읽지 못하게 막고(HttpOnly), 같은 사이트에서 보낸 요청에만 같이 보낸다(SameSite=Lax) | ✅ SCREEN-SPEC 13.1 의 2번, D-052, D-053, D-094 · 쿠키 이름·속성은 사용자 결정 |
| 여러 기기 | 기기마다 로그인 상태가 따로 있다. 한 기기의 로그아웃은 다른 기기에 영향이 없다 | ✅ D-054 |
| 확인 순서 | 요청을 받으면 ① 로그인 확인 → ② 식품 번호가 내 식품인지(없는 식품·남의 식품·처리된 식품은 똑같이 `not_found`), 분석 번호가 내 것이고 30분 안인지 → ③ 입력 검사 → ④ 기한 계산·저장 순으로 본다. 앞 단계에서 걸리면 뒤 단계는 보지 않는다 | ✅ D-061, D-063, D-090 · ✅ 순서 |
| 내 식품만 | 🔒 창구는 같은 한 곳에서 로그인 확인과 "내 식품만" 걸러 내기를 한다 | ✅ ARCHITECTURE 3절, D-061 |
| 요청 단위 | 요청 하나가 한 묶음이다. 중간에 실패하면 전부 되돌려 아무것도 바뀌지 않는다. **한꺼번에 등록(규칙표에 더하는 일 포함)과 탈퇴도 한 묶음이다** | ✅ OQ-04, D-110, D-136 |
| 오늘 날짜 | 서버 시계의 한국 시간이다. 날짜는 한국 시간 0시에 바뀐다. 코드에서 오늘은 `get_today()` 한 곳에서만 정한다 | ✅ D-087, D-088 |
| 날짜 모양 | 날짜는 `YYYY-MM-DD` 글자다. 시각은 쓰지 않는다 | ✅ D-031 |
| 판정은 API 만 | 여유·주의·임박·지남과 "달력에 보일지"는 API 만 계산한다. 저장하지 않고 요청할 때마다 계산한다. 화면은 색만 입힌다 | ✅ D-009, D-011, D-014, D-016 |
| 위험 식품 · 식품 종류 | 식품 응답의 `is_danger`, `danger_note`, `category` 는 저장하지 않고 규칙표에서 읽어 붙인다(직접 등록 식품의 `category` 는 등록할 때 고른 값). 상태 판정은 위험 식품도 다른 식품과 같은 기준이다 | ✅ D-164, D-166, D-168, 5절 48번 |
| 색 | 밝기와 포인트 색은 서버에 저장하지 않는다. 이 문서에는 색을 읽거나 저장하는 창구가 없다 | ✅ ARCHITECTURE 9절 36번, SCREEN-SPEC 9.5 |
| 입력 검사 | 화면이 먼저 알려 주고, 최종 판단은 API 가 한다. 화면을 거치지 않은 요청도 API 가 막는다 | ✅ D-010 |
| 성공 안내 | 따로 없다. 화면이 바뀐 것으로 안다 | ✅ SCREEN-SPEC 0절 |
| 중복 클릭 | 버튼을 눌러 보낸 쓰기·AI 요청은 처리가 끝날 때까지 화면이 다시 보내지 않는다. API 는 같은 요청이 두 번 왔는지 가려내지 않는다 | ✅ D-099, D-112 |
| 성공 상태 번호 | 만들기(`POST /auth/signup`, `POST /foods`, `POST /foods/manual`, **`POST /foods/bulk`**)는 **201**, 지우기(`DELETE /foods/{id}`)와 로그아웃, **탈퇴**는 본문 없는 **204**, 나머지(**사진 읽기·음식 추천·기록 조언·일반 조언** 포함)는 **200** | 삭제 204 는 ARCHITECTURE 3절, 나머지는 사용자 결정 |
| 목록 개수 | 제한을 두지 않는다. 이름·단위 글자 수도 제한하지 않는다. 한꺼번에 등록할 수 있는 개수에도 상한이 없다 | ✅ D-025, D-111 |
| AI 호출 | AI 는 API 가 부른다. 화면이 AI 에 직접 닿지 않는다. 사진 읽기는 **60초**, 음식 추천 · 기록 조언 · 일반 조언은 **30초**까지 기다리고, 넘거나 오류이거나 응답 모양이 규칙에 안 맞으면 `ai_failed` **502** 로 돌려준다(**일반 조언만** 미리 써 둔 조언으로 대신해 실패가 보이지 않는다). 사용 횟수 제한은 없다. 모델은 설정으로 바꿀 수 있고 기본은 Haiku 5.5 이다 | ✅ ARCHITECTURE 3절, D-131, D-132, D-123, D-157 |
| 사진 | 올린 사진은 AI 가 읽는 동안 메모리에만 있고 저장하지 않는다. 읽은 결과(글)만 내 계정으로 30분 보관한다 | ✅ D-102, ARCHITECTURE 4-4 |
| 인증 오류 구분 | 로그인하지 않았거나 30분이 지났으면 **401** `login_required`. 없는 것·남의 것·처리된 것은 모두 **404** `not_found`(분석 번호는 422 `analysis_expired`). **403 은 쓰지 않는다.** "권한이 없다"고 알리면 그 번호의 식품이 있다는 것이 드러나기 때문이다 | ✅ D-063, D-059 · 403 을 쓰지 않는 것은 5절 38번 |
| 화면의 기다리는 시간 | 화면은 서버보다 오래 기다린다. 사진 읽기는 **65초 이상**, 음식 추천 · 기록 조언 · 일반 조언은 **35초 이상**. 화면과 API 사이의 중간 단계(개발 서버)도 같은 시간 이상으로 맞춘다. 그보다 짧으면 서버는 성공했는데 화면은 실패로 보게 된다 | 5절 39번, 54번 |

### 0-1. 식품 한 건의 모양

식품을 돌려주는 창구는 모두 이 모양을 쓴다. 한 곳에서만 고친다.

| 칸 | 값 | 뜻 | 근거 |
|---|---|---|---|
| `id` | 글자(UUID 36자) | 식품 번호 | ✅ D-033 |
| `name` | 글자 | 이름 | ✅ D-032 |
| `storage` | `room` / `fridge` / `freezer` | 상온 / 냉장 / 냉동 | ✅ D-032 |
| `quantity` | 숫자 | 0보다 큰 수, 소수 둘째 자리까지 | ✅ D-027 |
| `unit` | 글자 | 단위 | ✅ D-032 |
| `purchase_date` | 날짜 글자 | 구매일 | ✅ D-032 |
| `expiry_date` | 날짜 글자 | 권장 기한 | ✅ D-032 |
| `source` | `rule` / `manual` | 규칙표 등록 / 직접 등록. **사진으로 등록한 식품도 `rule`** 이다 | ✅ D-029, D-032, D-134 |
| `status` | `none` / `eaten` / `discarded` | 처리 상태 | ✅ D-032 |
| `processed_date` | 날짜 글자 또는 `null` | 처리한 날짜. 처리하지 않았거나 되돌렸으면 `null` | ✅ ARCHITECTURE 3절, D-064, D-075 |
| `expiry_status` | `fresh` / `warning` / `soon` / `expired` 또는 `null` | 여유 / 주의 / 임박 / 지남 | ✅ ARCHITECTURE 3절, D-014 |
| `days_left` | 정수 또는 `null` | 기한까지 남은 날. 기한 당일은 0, 지났으면 음수(−1 = 하루 지남) | ✅ 칸 이름 (ARCHITECTURE 3절) · ✅ 음수로 지남 표현 |
| `show_on_calendar` | `true` / `false` 또는 `null` | 홈 달력에 보일지. 지난 지 4일 이상이면 `false` | ✅ ARCHITECTURE 3절, D-014 |
| `is_danger` | `true` / `false` | 위험 식품인지. 규칙표 식품이고 규칙표에서 같은 이름의 위험 여부가 참일 때만 `true`. 직접 등록 식품은 항상 `false` | ✅ ARCHITECTURE 3절, V-35, D-164, D-166 |
| `danger_note` | 글자 또는 `null` | 위험 이유 한 줄. `is_danger` 가 `true` 일 때만 글자, 아니면 `null` | ✅ ARCHITECTURE 3절, V-36 |
| `category` | `vegetable` / `fruit` / `meat` / `seafood` / `other` 또는 `null` | 식품 종류(채소 / 과일 / 육류 / 수산 / 그 밖). 규칙표 식품은 규칙표 값, 직접 등록 식품은 등록할 때 고른 값 | ✅ 칸 이름 (ARCHITECTURE 3절) · 값 이름은 5절 44번 |

- 처리된 식품(`status` 가 `eaten`·`discarded`)은 계산 칸 세 개(`expiry_status`, `days_left`, `show_on_calendar`)가 `null` 이다. (✅ ARCHITECTURE 3절)
- 위험 · 종류 칸 세 개(`is_danger`, `danger_note`, `category`)는 계산 칸이 아니라 처리된 식품에도 붙는다. 규칙표 식품인데 규칙표에서 이름을 찾을 수 없으면 `is_danger` 가 `false`, `danger_note` 와 `category` 가 `null` 이다. (5절 47번)
- 보관 방법별 가능 여부는 식품 응답에 없다. 규칙표 검색 결과에만 있다. (✅ SCREEN-SPEC 13.1 의 8번)

### 0-2. 오류의 모양

모든 실패는 같은 세 칸으로 돌려준다. (✅ ARCHITECTURE 3절)

```
{ "field": "quantity", "reason": "invalid_quantity", "message": "..." }
```

| 칸 | 뜻 |
|---|---|
| `field` | 문제가 된 입력칸 이름. 특정 칸 때문이 아니면 `null`. 한꺼번에 등록에서는 줄 위치를 함께 적는다(예: `items.2.quantity`) |
| `reason` | 이유 이름. 화면이 이것을 보고 어디에 안내를 붙일지, 로그인 화면으로 갈지, 기한 입력칸을 열지 정한다 |
| `message` | 쉬운 문구. 문구는 코드 한 곳에서만 고친다 |

상태 번호는 입력 오류 **422**, 없는 식품 **404**, 기한 다시 적기 **409**, 저장·불러오기 실패 **500**, AI 실패 **502**, 로그인 관련은 3절 표를 따른다. (✅ ARCHITECTURE 3절)

- ✅ 주소와 메서드는 ARCHITECTURE 3절에 모두 정해져 있다.
- 기록 화면은 한 번 열 때 D1 과 D2 를 함께 부른다. 하나라도 실패하면 기록 화면 전체가 "불러오지 못함"이다. (✅ SCREEN-SPEC 7.5 의 "숫자를 불러오지 못함"을 두 창구에 같이 적용)
- 상태 알약 · 보관 방법 · 식품 종류 드롭다운 · 막대 달력 주 넘기기 · 전체 달력 · 날짜 목록 창은 새 창구 없이 화면이 A1 목록 하나로 그린다. (✅ ARCHITECTURE 9절 31번)
- J1 은 사진 읽기(F1) · 음식 추천(G1) 요청과 함께 부른다(확인 중 화면). 기록 조언(I1)에는 확인 중 화면이 없고 '조언 받기' 버튼이 흐려진다. (SCREEN-SPEC 15절, 7.6)
- 등록은 셋으로 나눈다(A2 규칙표 / A3 직접 / F2 사진으로 읽은 목록). 사진으로 등록하는 일은 둘이다(F1 읽기 / F2 등록). 상세 화면의 동작은 정보 고치기(A5, 보관 방법 포함)와 처리(A7)로 나눈다. 홈 휴지통 선택창의 처리·삭제도 같은 A7 · A8 을 쓴다. SCREEN-SPEC 4.8, 5절, 6절이 이미 나눠 놓았다.

## 2. 창구별 상세

### 2-1. 가입 · 로그인 · 로그아웃 (US-012)

#### B1. 가입 — `POST /auth/signup`

| 항목 | 내용 |
|---|---|
| 보내는 칸 | `email`, `password` |
| 검사 | 이메일은 @ 와 점이 있는 모양까지만 (V-15 이전에 모양 확인, D-095). 비밀번호는 8자 이상이고 영문·숫자·특수문자를 모두 포함 (V-15, D-047). 이미 가입된 이메일이면 불가 (V-16, D-058) |
| 성공 | **201**. 계정을 만들고 이 기기의 로그인 상태를 만든다(쿠키). 본문은 `{ "email": "..." }` ✅. 화면은 홈으로 간다 |
| 첫 가입일 때 | 기존 식품을 이 계정으로 한 번만 옮긴다. 옮기다 실패해도 **가입은 성공**한다. 옮기기는 전부 취소되고, 첫 계정이 다음에 로그인할 때 성공할 때까지 다시 시도한다 (D-096) |
| 실패 | 이메일 모양이 아님 `invalid_email` 422 / 비밀번호 규칙 위반 `weak_password` 422 / 이미 가입된 이메일 `email_taken` 409 / 저장 실패 500 |
| 근거 | US-012, D-042 ~ D-047, D-058, D-081, D-093, D-095, D-096, 시나리오 1 |

- 비밀번호는 원문으로 저장하지 않고 사용자마다 다른 솔트를 붙여 해시로 저장한다. (D-093)
- 가입할 때 이메일 인증은 하지 않는다. (D-048)

#### B2. 로그인 — `POST /auth/login`

| 항목 | 내용 |
|---|---|
| 보내는 칸 | `email`, `password` |
| 성공 | **200**. 이 기기의 로그인 상태를 새로 만든다(쿠키). 다른 기기의 로그인 상태는 그대로다. 본문은 `{ "email": "..." }` ✅. 화면은 홈으로 간다 |
| 기존 식품 옮기기 | 첫 계정이 아직 옮기지 못했다면 이때 다시 시도한다. 실패해도 **로그인은 성공**한다 (D-096) |
| 실패 | 이메일이나 비밀번호가 틀림 `login_failed` 401. **어느 쪽이 틀렸는지, 그 이메일이 가입돼 있는지 알리지 않는다** (V-17, D-057). 틀려도 횟수 제한은 없다 (D-049). 저장 실패 500 |
| 근거 | US-012, D-049, D-054, D-057, D-081, D-096, 시나리오 2 |

- 이메일 모양이나 비밀번호 규칙은 로그인에서는 검사하지 않는다. 맞지 않는 값은 모두 `login_failed` 로 돌려준다. (✅ 어느 쪽이 틀렸는지 알리지 않으려는 D-057 의 취지)

#### B3. 로그아웃 — `POST /auth/logout` 🔒

| 항목 | 내용 |
|---|---|
| 성공 | **204**. 이 기기의 로그인 상태만 끝낸다. 다른 기기는 유지된다. 화면은 로그인 화면으로 간다. 로그인 화면을 뺀 모든 화면의 로그아웃 버튼이 이 창구를 부른다 |
| 실패 | 이미 로그인 상태가 아님 `login_required` 401 (화면은 어차피 로그인 화면으로 간다). 저장 실패 500 |
| 근거 | US-012, D-054, D-060, D-130, 시나리오 3 |

#### 로그인 필요 · 30분 만료 (모든 🔒 창구)

- 로그인하지 않았거나, 마지막 사용 뒤 30분이 지난 요청은 `login_required` **401** 로 거절한다. 화면은 이것을 보고 로그인 화면으로 보낸다. 입력 중이던 내용은 사라진다. (V-19, D-053, D-055, D-059)
- 거절된 요청은 마지막 사용 시각을 갱신하지 않는다. (✅ 이미 끝난 로그인 상태가 되살아나지 않게 하려는 것)
- 다시 로그인하면 홈으로 간다. (D-056)
- 앱을 켤 때 이미 로그인된 상태인지 따로 묻는 창구는 없다. 화면은 홈의 목록(A1)을 불러 보고, 401 이면 로그인 화면으로 간다. (✅ 4절 참고)

### 2-2. 규칙표 검색 (US-001)

#### C1. `GET /rules?q=이름` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 것 | `q` — 검색어 |
| 성공 | `{ "items": [ { "name", "default_storage", "disallowed_storages", "category" } ] }` ✅. 이름이나 별칭에 검색어가 들어 있으면 찾는다. 별칭으로 찾아도 결과에는 식품 이름이 나오고, 같은 식품은 한 번만 나온다. 이름순이다. 빈 검색어이거나 찾는 것이 없으면 `items` 가 빈 목록이다(실패가 아니라 성공) |
| 실패 | 규칙표를 못 읽음 500 |
| 근거 | US-001, D-005, D-007, D-035, D-133, 시나리오 6 |

| 칸 | 값 | 뜻 |
|---|---|---|
| `name` | 글자 | 규칙표의 식품 이름 |
| `default_storage` | `room` / `fridge` / `freezer` | 기본 보관 방법. 등록 화면이 미리 선택해 둔다 (OQ-02) |
| `disallowed_storages` | 보관 방법 값의 목록 | 고를 수 없는 보관 방법. 화면이 흐리게 보이고 누를 수 없게 한다 (D-005). 없으면 빈 목록 |
| `category` | `vegetable` / `fruit` / `meat` / `seafood` / `other` | 규칙표의 식품 종류. 규칙표에서 고른 식품의 등록 입력 화면이 종류 캡슐로 보인다 (D-164) |

- 오타 보정은 하지 않는다. (PRD 4-3)
- 모든 계정이 같은 규칙표를 읽는다. 규칙표에는 처음 30개와 사진으로 등록할 때 더해진 식품이 함께 있다. 다른 계정이 직접 등록한 식품은 여기에 나오지 않는다. (D-091, D-133)
- 사진 등록으로 더해진 식품은 **별칭이 없다.** 그래서 이름이 검색어에 들어 있을 때만 찾아진다. (ARCH 4-3)
- 화면은 이 결과로 상세 화면의 불가 보관 방법도 흐리게 보인다. 이름이 같은 항목을 찾는다. 못 찾으면 흐리게 보이지 못하고, 저장할 때 API 가 거절한다. (SCREEN-SPEC 13.1 의 8번, 10번)

### 2-3. 식품 (US-001, US-003 ~ US-008, US-011)

#### A1. 홈 목록 — `GET /foods` 🔒

| 항목 | 내용 |
|---|---|
| 성공 | `{ "today": "YYYY-MM-DD", "items": [식품 한 건, ...] }` ✅ (칸 이름 `today` 는 ✅ ARCHITECTURE 3절). **내 식품 중 처리 상태가 `none` 인 것만** 돌려준다. 식품마다 `expiry_status`·`days_left`·`show_on_calendar` 와 **`is_danger`·`danger_note`·`category`** 가 붙는다 |
| 정렬 | 기한이 빠른 순 → 구매일이 이른 순 → 이름순 (D-015, D-033) |
| 실패 | 목록을 못 불러옴 500. 클라우드 DB 에 연결하지 못해도 같다 |
| 근거 | US-007, US-008, US-026, US-029, US-040, D-009, D-014, D-015, D-021, D-061, D-087, D-146, D-164 |

- 상태 기준 (V-12, D-014): 남은 날 6 이상 `fresh` / 3~5 `warning` / 0~2 `soon`(기한 당일 포함) / 기한 다음 날부터 `expired`. 모든 식품에 같은 기준, 날 단위.
- 지남 식품은 처리할 때까지 목록에 남는다. 지난 지 4일 이상이면 `show_on_calendar` 만 `false` 가 되고 목록에는 남는다.
- 식품이 하나도 없으면 `items` 가 빈 목록이다. 화면이 안내 문구와 등록 버튼을 보인다. (OQ-05)
- 달력의 "오늘" 세로선은 `today` 로 그린다. 화면 시계는 쓰지 않는다. (D-021)
- 화면이 이 목록 하나로 상태 알약의 수, 알약 · 보관 방법 · 식품 종류 거르기, 막대 달력의 주 넘기기, 전체 달력의 날짜 배치를 한다. 거르는 데는 `expiry_status`, `storage`, `category` 를, 전체 달력에는 `purchase_date`, `expiry_date` 를 쓴다. 알약을 누르거나 주를 넘길 때마다 API 를 다시 부르지 않는다. (✅ ARCHITECTURE 9절 31번, D-016, D-192)
- 지난 지 4일 이상인 식품은 `show_on_calendar` 만 `false` 이고, 전체 달력에서는 보인다. (D-146)

#### A2. 규칙표 식품 등록 — `POST /foods` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | `name`(규칙표의 이름 또는 별칭과 정확히 같아야 함. 별칭으로 보내도 저장되는 이름은 규칙표의 정식 이름), `quantity`, `unit`, `purchase_date`, `storage` (✅ ARCHITECTURE 3절). `purchase_date` 는 필수이고, "기본 오늘"은 화면이 홈 목록이 준 `today` 로 채워 보낸다 (A3 도 같다) |
| 하는 일 | 검사 → 기한 = 구매일 + 그 보관 방법의 최대 보관 일수 (V-08) → 구매일이 기한보다 뒤인 조합 확인 (V-07) → **내 식품으로** 저장. `source` = `rule`, `status` = `none` |
| 성공 | **201**, 만들어진 식품 |
| 실패 | 아래 표 |
| 근거 | US-001, D-003, D-005, D-027, D-061, 시나리오 6 |

| 실패 | `reason` | 상태 | `field` |
|---|---|---|---|
| 이름 · 단위가 비었음 | `required` | 422 | `name` 또는 `unit` |
| 수량이 비었음 · 0 이하 · 숫자가 아님 · 소수 셋째 자리 이상 | `invalid_quantity` | 422 | `quantity` |
| 구매일이 올바른 날짜가 아님 | `invalid_date` | 422 | `purchase_date` |
| `storage` 가 세 값 중 하나가 아니거나 없음 | `invalid_storage` | 422 | `storage` |
| 규칙표의 이름도 별칭도 아님 | `rule_not_found` | 422 | `name` |
| 규칙표가 "불가"로 정한 보관 방법 | `storage_not_allowed` | 422 | `storage` |
| 저장 실패 | `server_error` | 500 | `null` |

- 구매일은 미래 날짜도 가능하다. (OQ-03)
- 응답 식품의 `is_danger`, `danger_note`, `category` 는 규칙표 값이다. (0-1절)
- 규칙표 식품에서는 구매일이 기한보다 뒤가 되는 조합이 생기지 않는다(기한 = 구매일 + 양수 일수). V-07 은 이 창구에서 계속 확인하지만 실패 이유는 따로 두지 않는다.

#### A3. 직접 등록 — `POST /foods/manual` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | A2 의 칸(`name`, `quantity`, `unit`, `purchase_date`, `storage`) + **`category`(식품 종류, 필수)** + `expiry_date`(날짜) **또는** `expiry_in_days`(며칠 뒤) 중 하나 (✅ ARCHITECTURE 3절, 9절 30번) |
| 하는 일 | 검사 → 기한 정하기(`expiry_in_days` 면 구매일 + N일, V-06, D-002) → V-05, V-07 확인 → 직접 적은 기한 그대로 **내 식품으로만** 저장. `source` = `manual`, `status` = `none`, `category` 는 보낸 값. 규칙표에는 더하지 않는다 (D-091) |
| 성공 | **201**, 만들어진 식품 |
| 근거 | US-003, D-002, D-003, D-091, V-41, 시나리오 7 |

| 실패 | `reason` | 상태 | `field` |
|---|---|---|---|
| 이름 · 단위가 비었음 | `required` | 422 | `name` 또는 `unit` |
| 수량 오류 | `invalid_quantity` | 422 | `quantity` |
| 구매일이 올바른 날짜가 아님 | `invalid_date` | 422 | `purchase_date` |
| `storage` 가 세 값 중 하나가 아니거나 없음 | `invalid_storage` | 422 | `storage` |
| 보낸 `expiry_date` 가 올바른 날짜가 아님 | `invalid_date` | 422 | `expiry_date` |
| `category` 가 다섯 값 중 하나가 아니거나 없음 (V-41) | `invalid_category` | 422 | `category` |
| 기한을 안 보냈거나, 두 가지를 모두 보냄 | `expiry_input_invalid` | 422 | `expiry_date` |
| 기한이 오늘보다 과거 (V-05) | `expiry_in_past` | 422 | `expiry_date` |
| 기한이 구매일보다 앞 (V-07, D-003) | `purchase_after_expiry` | 422 | `expiry_date` |
| `expiry_in_days` 가 정수가 아니거나 음수 | `invalid_expiry_in_days` | 422 | `expiry_in_days` |
| 규칙표에 이미 있는 이름 (별칭 포함) | `rule_name_exists` | 422 | `name` |
| 저장 실패 | `server_error` | 500 | `null` |

- 보관 방법은 상온·냉장·냉동 모두 가능하다. (시나리오 7)
- 직접 등록 식품은 위험 표시가 없다(`is_danger` 가 항상 `false`). (D-166)
- `expiry_in_days` 로 정한 기한이 오늘보다 과거가 되는 경우(구매일이 과거이고 N 이 작을 때)도 `expiry_in_past` 로 거절한다. (V-05)
- 규칙표의 이름이나 별칭으로 직접 등록하려 하면 거절한다. 규칙표는 사진 등록으로 늘어나므로 그렇게 더해진 이름도 같다. 화면은 검색 결과가 없을 때만 직접 등록으로 보내지만, 화면을 거치지 않은 요청도 API 가 막아야 하고(D-010), 직접 등록 식품이 규칙표 이름을 쓰면 A5 의 "이름을 고쳐 규칙표 이름이 되면 `rule` 이 된다"와 어긋나기 때문이다.

#### A5. 정보 고치기 — `PATCH /foods/{id}` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | 바꿀 것만 보낸다: `name`, `quantity`, `unit`, `purchase_date`, `expiry_date`(기한 다시 적기 때만), **`storage`**(정보 고치기에서 보관 방법도 함께 바꿀 때), **`category`**(직접 등록 식품의 종류. 직접 등록 식품만 바꿀 수 있다) (✅ ARCHITECTURE 3절). 안 보낸 칸은 그대로다. **여러 칸이 함께 오면 이름 → 보관 방법 → 구매일 순서로 기한을 다시 계산하고 한 묶음으로 저장한다** (V-39) |
| 성공 | **200**, 바뀐 식품. 화면은 수정 칸을 닫고 **같은 상세 화면에 머문다** (D-173) |
| 근거 | US-004, US-005, US-042, D-003, D-004, D-006, D-022, D-023, D-024, D-026, D-029, D-134, D-172, D-173, D-174, OQ-09, OQ-10, OQ-11, 시나리오 11, 12 |

**기한이 정해지는 방식**

| 바뀐 것 | 결과 | 근거 |
|---|---|---|
| 구매일 | 규칙표 식품(`source` = `rule`): 구매일이 움직인 일수만큼 기한도 같이 옮긴다. 새 기한 = 기존 기한 + (새 구매일 − 옛 구매일). 직접 등록 식품(`source` = `manual`): 기한은 그대로. 구매일이 기한보다 뒤가 되면 저장하지 않는다. 구매일은 미래 날짜도 허용 | D-003, D-024 |
| 이름 → 규칙표에 있는 이름 (별칭 포함. 별칭으로 바꿔도 저장되는 이름은 정식 이름) | 규칙표 기준으로 기한을 다시 계산한다. 지금까지 쓴 수명 비율을 이어받고 소수 날짜는 내림한다(V-09). 직접 등록 식품이면 `source` 가 `rule` 로 바뀐다. 이 뒤로 위험 여부 · 이유 · 종류는 새 이름의 규칙표 값을 읽어 붙인다 | D-004, D-029, D-164 |
| 이름 → 규칙표의 이름도 별칭도 아닌 이름 | 규칙표 식품이든 직접 등록 식품이든 **기한을 다시 적어야 한다.** `expiry_date` 없이 보내면 409 `expiry_required`. 규칙표 식품이었다면 `source` 가 `manual` 이 된다. 위험 표시는 없어지고(D-166) 종류는 그 식품의 직접 등록 종류가 된다 | D-029, D-166, OQ-10, PRD 4-4 |
| 수량 · 단위 | 바뀐 수량·단위만 보인다. 기한과 상태는 그대로 | D-027 |
| **보관 방법** — 규칙표 식품 (사진으로 등록한 식품 포함) | 새 남은 기간 = (1 − 지금까지 보관한 기간 ÷ 지금 방법의 최대 보관 기간) × 새 방법의 최대 보관 기간. 소수 날짜는 내림(D-004). 구매일이 미래면 보관한 기간은 0일(D-022). 새 기한은 이 계산을 D-006·D-022 에 적힌 그대로 따라 정한다 | D-004, D-006, D-022, D-134 |
| **보관 방법** — 이미 기한이 지난 식품 | 같은 식으로 계산한다. 계산 결과가 음수이거나 새 기한이 오늘보다 뒤가 되지 않으면 바꿀 수 없다. 새 기한이 오늘보다 뒤가 되면 바뀌고 더 이상 지남이 아니다 | D-006 |
| **보관 방법** — 직접 등록 식품 (다른 보관 방법으로 바꿀 때) | 계산할 규칙표가 없으므로 기한을 다시 적어야 한다. `expiry_date` 없이 보내면 409 `expiry_required` | D-023 |
| **보관 방법** — 같은 보관 방법 | 규칙표 식품이든 직접 등록 식품이든 기한 그대로 성공(200)으로 처리한다. 직접 등록 식품도 기한을 다시 적게 하지 않고, 함께 온 `expiry_date` 는 무시한다. **이 행이 위 보관 방법 행들보다 먼저 적용된다** | D-006, SCREEN-SPEC 6.3, USER-WORKFLOW 12 |
| **종류** — 직접 등록 식품 | 종류만 바뀐다. 기한과 상태는 그대로. 다섯 값 중 하나여야 한다 (V-41) | 사용자 요청, V-41 |
| **종류** — 규칙표 식품 | 보내도 무시한다. 종류는 규칙표 값을 읽어 붙이는 것이라 식품에 저장하지 않는다 | 5절 46번 |
| 이름과 구매일을 함께 | 이름 규칙을 먼저 적용하고, 그 기한에 구매일 이동을 적용한다 | D-026 |
| 이름과 보관 방법을 함께 | 이름 규칙을 먼저 적용한 뒤, 그 결과의 식품을 기준으로 보관 방법 규칙을 적용한다. 이름이 규칙표에 없어 직접 등록 식품이 되면 기한을 다시 적어야 하고, 적은 기한이 최종이다(보관 방법은 값만 바뀐다) | V-39, 5절 55번 |

**실패**

| 실패 | `reason` | 상태 | `field` |
|---|---|---|---|
| 이름 · 단위를 비움 | `required` | 422 | `name` 또는 `unit` |
| 수량이 0 이하 · 숫자가 아님 · 소수 셋째 자리 이상 | `invalid_quantity` | 422 | `quantity` |
| 구매일이 올바른 날짜가 아님 | `invalid_date` | 422 | `purchase_date` 또는 `expiry_date` |
| 구매일을 (직접 적은) 기한보다 뒤로 바꿈 (V-07) | `purchase_after_expiry` | 422 | `purchase_date` |
| 규칙표에 없는 이름으로 바꾸는데 이미 기한이 지난 식품 (V-11) | `rename_expired_not_allowed` | 422 | `name` |
| 규칙표에 없는 이름으로 바꾸면서 적은 기한이 오늘보다 과거 (V-05) | `expiry_in_past` | 422 | `expiry_date` |
| 새 기한이 구매일보다 앞 | `purchase_after_expiry` | 422 | `expiry_date` |
| 규칙표에 없는 이름으로 바꾸는데 기한을 안 적음 | `expiry_required` ✅ | **409** | `expiry_date` |
| `storage` 가 세 값 중 하나가 아님 | `invalid_storage` | 422 | `storage` |
| 규칙표가 "불가"로 정한 보관 방법 (V-04) | `storage_not_allowed` | 422 | `storage` |
| 보관 방법을 바꾸는데 규칙표 식품의 이름을 규칙표에서 찾을 수 없음(규칙표 내용이 바뀜) | `rule_not_found` | 422 | `storage` |
| 이미 지난 식품인데 계산 결과가 음수이거나 새 기한이 오늘보다 뒤가 되지 않음 (V-10) | `storage_change_not_allowed` | 422 | `storage` |
| 직접 등록 식품을 다른 보관 방법으로 바꾸는데 기한을 안 적음 | `expiry_required` ✅ | **409** | `expiry_date` |
| 직접 등록 식품을 다른 보관 방법으로 바꾸는데 적은 기한이 오늘보다 과거 | `expiry_in_past` | 422 | `expiry_date` |
| 직접 등록 식품을 다른 보관 방법으로 바꾸는데 적은 기한이 구매일보다 앞 | `purchase_after_expiry` | 422 | `expiry_date` |
| `category` 가 다섯 값 중 하나가 아님 (V-41) | `invalid_category` | 422 | `category` |
| 없는 · 처리된 · 남의 식품 | `not_found` ✅ | 404 | `null` |
| 저장 실패 (한 칸이라도 어기면 전부 취소) | `server_error` | 500 | `null` |

- `expiry_required` 는 실패가 아니라 정해진 응답 하나다. 화면이 알아보고 같은 화면에 기한 입력칸을 연 뒤, `expiry_date` 를 채워 같은 창구를 다시 부른다. 이때 아무것도 저장되지 않는다. (✅ ARCHITECTURE 3절)
- 이미 기한이 지난 식품은 규칙표에 없는 이름으로 바꿀 수 없으므로, 그 경우에는 `expiry_required` 가 아니라 `rename_expired_not_allowed` 를 먼저 돌려준다. (✅ PRD 4-4, V-11. 오늘 이후 날짜를 적는 길이 막혀 있어 다시 적게 해도 소용이 없기 때문이다.)
- 이름과 구매일을 함께 바꿀 때 구매일 규칙은 이름 규칙이 정한 기한에 대해 확인한다. (D-026)
- 기한을 다시 적을 필요가 없는 수정에 `expiry_date` 가 함께 오면 무시한다(보낸 값을 쓰지 않는다). 화면이 기한 입력칸을 연 뒤에도 같은 칸 모양으로 다시 보내기 때문이다.
- 규칙표에서 이름을 못 찾는 규칙표 식품(규칙표 내용이 바뀐 경우)은 상세 화면이 열린다. 보관 방법을 바꾸려 하면 `rule_not_found` 로 거절하고, 기한을 직접 적게 하는 길은 열지 않는다. (SCREEN-SPEC 13.1 의 10번, D-010)
- 칸 하나라도 어기면 아무것도 저장하지 않고, 먼저 걸린 오류 하나만 돌려준다. 정보 고치기를 저장하면 상세 화면에 머문다. (V-39, D-173)
- 화면은 이 계산을 하지 않는다. 계산과 판정은 API 가 한다. (D-009, D-016)

#### A6. (없앰) 보관 방법 변경 — `PATCH /foods/{id}/storage`

정보 고치기가 한 창구(A5)로 합쳐져서 이 창구는 만들지 않는다. 같은 일(규칙표 식품은 비율을 이어받아 기한 다시 계산, 직접 등록 식품은 기한 다시 적기)을 A5 가 `storage` 칸으로 한다. 이전 버전 A6 의 규칙과 실패 표는 A5 의 표로 옮겼다. 번호는 이어 붙이기 위해 남겨 둔다. (✅ ARCHITECTURE 3절, 9절 34번, D-172, 5절 42번)

#### A7. 다 먹음 / 버림 — `PATCH /foods/{id}/process` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | `status` = `eaten` 또는 `discarded` (✅ ARCHITECTURE 3절) |
| 하는 일 | 처리 상태를 바꾸고 **처리한 날짜(서버 한국 시간 오늘)를 `processed_date` 에 저장**한다. 행은 남긴다 (D-064, D-013) |
| 성공 | **200**, 처리된 식품(계산 칸 세 개는 `null`, `processed_date` 가 채워짐). 화면은 홈으로 간다. 홈 목록에서 빠진다 |
| 실패 | `status` 가 두 값 중 하나가 아님 `invalid_status` 422 (`field` = `status`) / 없는 · **이미 처리된** · 남의 식품 `not_found` 404 / 저장 실패 `server_error` 500 |
| 근거 | US-011, D-008, D-013, D-064, D-087, D-090, 시나리오 13 |

- 화면은 확인 창에서 확인한 뒤에만 이 창구를 부른다. 확인 창에서 취소하면 요청을 보내지 않는다. (SCREEN-SPEC 6.4, 13.1 의 7번)
- 이미 처리된 식품에 다시 요청하면 `not_found` 다. 다 먹음을 버림으로 바꾸는 재처리도 안 된다. (V-14, V-20, D-090)
- 홈 목록 줄의 휴지통 선택창에서 '다 먹음' · '버림'을 고른 뒤에도 같은 창구를 부른다. 선택창 다음의 확인 창에서 확인한 뒤에만 보낸다. (D-143, D-144, 시나리오 25)

#### A8. 삭제 — `DELETE /foods/{id}` 🔒

| 항목 | 내용 |
|---|---|
| 성공 | **204**, 본문 없음. 식품을 **완전히** 지운다. 기록 숫자에도, 처리한 식품 목록에도 남지 않는다. 되돌릴 수 없다 (D-013, D-070, D-078) |
| 실패 | 없는 · **처리된** · 남의 식품 `not_found` 404 / 삭제 실패 `server_error` 500 |
| 근거 | US-006, D-008, D-013, D-063, D-070, D-078, D-090, 시나리오 14 |

- 처리된 식품(다 먹음·버림)은 삭제할 수 없다. 기록에서 먼저 홈으로 되돌린 뒤 삭제한다. (V-20, D-090)
- 화면은 확인 창에서 확인한 뒤에만 이 창구를 부른다. (OQ-06)
- 휴지통 선택창에서 '삭제'를 고른 뒤에도 같은 창구를 부른다. 확인 창을 거친 뒤에만 보낸다. (D-143, D-144)

### 2-4. 기록 (US-013, US-015)

#### D1. 기록 숫자 — `GET /records/summary` 🔒

| 항목 | 내용 |
|---|---|
| 하는 일 | **내 식품만**으로 다섯 가지 숫자를 센다. 삭제한 식품은 세지 않는다 (V-22, D-070) |
| 성공 | 아래 모양 ✅ |
| 실패 | 숫자를 못 불러옴 500 |
| 근거 | US-013, D-065 ~ D-071, D-087, D-088, 시나리오 15 |

```
{
  "eaten":      { "year": 0, "month": 0 },
  "discarded":  { "year": 0, "month": 0 },
  "food_kinds": 0,
  "by_storage": { "room": 0, "fridge": 0, "freezer": 0 },
  "by_category": { "vegetable": 0, "fruit": 0, "meat": 0, "seafood": 0, "other": 0 },
  "by_status":  { "fresh": 0, "warning": 0, "soon": 0, "expired": 0 }
}
```

| 칸 | 센 것 | 근거 |
|---|---|---|
| `eaten.year` · `eaten.month` | `processed_date` 가 올해 / 이번 달에 드는 다 먹음 식품 수. 올해·이번 달은 서버 한국 시간 오늘 기준 | D-065, D-066, D-088 |
| `discarded.year` · `discarded.month` | 같은 기준의 버림 식품 수 | D-065, D-066 |
| `food_kinds` | 처리 상태가 `none` 인 식품의 **이름 종류 수**. 같은 이름은 한 종류. 우유를 두 번 샀어도 1 | D-067 |
| `by_storage` | 처리 상태가 `none` 인 식품을 상온 / 냉장 / 냉동 별로 센 수 | D-068 |
| `by_category` | 처리 상태가 `none` 인 식품을 식품 종류별로 센 수. 종류는 A1 과 같은 방식(규칙표 식품은 규칙표 값, 직접 등록 식품은 등록할 때 고른 값, 못 찾으면 `other`)으로 요청할 때마다 계산한다 | D-164 |
| `by_status` | 처리 상태가 `none` 인 식품을 여유 / 주의 / 임박 / 지남 별로 센 수. 판정은 A1 과 같은 판정을 쓴다 (V-12). **달력에 안 보이는 지난 지 4일 이상 식품도 `expired` 에 센다** | D-069, D-009 · ✅ 지난 지 4일 이상도 포함 |

- 다 먹음·버림·현재 식품이 모두 없으면 모든 숫자가 0 이다. 화면이 0 과 함께 안내 문구와 등록 버튼을 보인다. 이것은 실패가 아니다. (D-071)
- 같은 이름은 글자가 완전히 같을 때만 한 종류로 센다. (✅ D-067 은 "이름 기준"만 말한다)
- 로그인 이전에 이미 처리한 기존 식품은 옮긴 날을 처리한 날로 센다. (D-045)

#### D2. 처리한 식품 목록 — `GET /records/foods` 🔒

| 항목 | 내용 |
|---|---|
| 하는 일 | 내 식품 중 `eaten`·`discarded` 인 것을 **전체**, **최근 처리한 순**으로, 다 먹음과 버림을 **나눠서** 돌려준다 (D-073, D-074) |
| 성공 | `{ "eaten": [ ... ], "discarded": [ ... ] }` ✅. 각 줄은 `id`, `name`, `quantity`, `unit`, `processed_date`, `category`(A1 과 같은 방식으로 붙인 식품 종류. 못 찾으면 `null`) |
| 실패 | 목록을 못 불러옴 500 |
| 근거 | US-013, US-015, D-064, D-073, D-074, SCREEN-SPEC 7.3, 13.1 의 5번 |

- 한 줄에 이름 · 수량 · 처리한 날짜가 보이고, 되돌릴 식품을 고르는 데는 `id` 가 쓰인다. 단위는 수량과 함께 보여야 해서 같이 준다. (SCREEN-SPEC 13.1 의 5번 · ✅ `unit`)
- 처리한 식품이 하나도 없으면 두 목록이 모두 비어 있다. 화면이 "되돌릴 식품이 없다"는 안내를 보인다. (US-015)
- 처리한 날짜가 같은 식품끼리는 이름순이다. 홈 목록의 마지막 기준(D-015)과 맞춘 것이다.

#### D3. 홈으로 되돌리기 — `PATCH /foods/{id}/restore` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | 없음 |
| 하는 일 | 처리 상태를 `none` 으로, `processed_date` 를 `null` 로. 이름·수량·단위·구매일·보관 방법·기한은 처리하기 전 그대로 (V-21, D-075, D-076) |
| 성공 | **200**, 되돌려진 식품(계산 칸이 다시 계산되어 붙음). 기한이 지난 뒤 처리한 식품은 기한과 오늘 날짜로 다시 판정되어 `expired` 가 된다. 처리할 때까지 홈 목록에 남는다 (D-077) |
| 실패 | 없는 · **처리되지 않은** · 남의 식품 `not_found` 404 / 저장 실패 `server_error` 500 |
| 근거 | US-015, D-072, D-075 ~ D-078, D-090, 시나리오 16 |

- 되돌릴 때 기한을 다시 계산하거나 다시 적게 하지 않는다. (D-076)
- 삭제한 식품은 기록에도 없으므로 되돌릴 수 없다. (D-078)
- 처리되지 않은 식품에 요청하면 없는 식품처럼 `not_found` 로 돌려준다. (✅ D-008 의 통일 원칙)

### 2-5. 사진으로 등록 (US-017 ~ US-020)

#### F1. 사진 읽기 — `POST /photos/analyze` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 것 | 사진 한 장. 칸 이름은 `image` 이고 파일로 보낸다 ✅ (ARCHITECTURE 3절) |
| 검사 | 한 번에 한 장, 형식은 jpg·png·webp, 크기는 5MB 이하 (V-23, D-101) |
| 하는 일 | 사진을 AI 에게 보내 **가공하지 않은 신선식품**의 이름과 보관 정보(권장 보관 방법, 방법별 최대 보관기간, 금지된 보관 방법)와 **위험 여부(위험이면 이유 한 줄) · 식품 종류**, 영수증 날짜를 받는다 (60초까지 기다림). 응답 모양을 검사해 규칙(V-26 · V-36 의 모양)에 안 맞는 식품(**위험 여부가 없거나 알아볼 수 없는 줄, 위험인데 이유 한 줄이 없는 줄** 포함)은 목록에서 뺀다. 이름이 규칙표에 있으면(이름 또는 별칭이 글자 그대로 같을 때) **규칙표 값**을, 없으면 AI 가 알려 준 값을 쓴다(위험 여부 · 이유 · 종류도 같다, D-190, D-191). 구매일은 영수증에서 읽은 날짜이고, 못 읽으면 `today` 다 (D-106, D-107). 결과(글)를 **내 계정으로 30분 보관**하고 `analysis_id` 를 준다. **사진은 저장하지 않는다** (D-102) |
| 성공 | **200**. 아래 모양 ✅ (ARCHITECTURE 3절) |
| 실패 | 아래 표 |
| 근거 | US-017, US-018, D-100 ~ D-107, D-131, D-135, D-164, D-165, D-190, D-191, 시나리오 8 |

```
{
  "analysis_id": "...",
  "items": [
    {
      "item_no": 0,
      "name": "우유",
      "recommended_storage": "fridge",
      "storages": [
        { "storage": "room",    "allowed": false, "max_days": null },
        { "storage": "fridge",  "allowed": true,  "max_days": 7 },
        { "storage": "freezer", "allowed": true,  "max_days": 30 }
      ],
      "purchase_date": "2026-11-03",
      "from_rule": true,
      "is_danger": false,
      "danger_note": null,
      "category": "other"
    }
  ]
}
```

| 칸 | 값 | 뜻 |
|---|---|---|
| `analysis_id` | 글자 또는 `null` | 사진 읽기 결과 번호. 한꺼번에 등록(F2)에 되돌려 보낸다. 식품이 하나도 없으면 보관하지 않고 `null` |
| `items[].item_no` | 정수 | 이 결과 안에서 줄을 구분하는 번호 (0부터) |
| `items[].name` | 글자 | 식품 이름. 규칙표에 있으면 규칙표의 정식 이름 |
| `items[].recommended_storage` | `room` / `fridge` / `freezer` | 권장 보관 방법. 확인 화면이 미리 선택해 둔다 |
| `items[].storages` | 방법 셋의 목록 | 방법마다 `storage`, `allowed`(고를 수 있는지), `max_days`(최대 보관기간, 고를 수 없으면 `null`). 금지된 방법은 `allowed` 가 `false` 다 |
| `items[].purchase_date` | 날짜 글자 | 구매일 기본값. 영수증에서 읽은 날짜, 못 읽으면 오늘 |
| `items[].from_rule` | `true` / `false` | 규칙표 값이면 `true`, AI 가 알려 준 값이면 `false` |
| `items[].is_danger` | `true` / `false` | 위험 식품인지. 규칙표에 같은 이름이 있으면 규칙표 값, 없으면 AI 가 알려 준 값 (AI 의 답 칸 이름 `danger` 를 이 이름으로 바꿔 준다, 5절 49번) |
| `items[].danger_note` | 글자 또는 `null` | 위험 이유 한 줄. `is_danger` 가 `true` 일 때만 글자 |
| `items[].category` | `vegetable` / `fruit` / `meat` / `seafood` / `other` | 식품 종류. 규칙표에 같은 이름이 있으면 규칙표 값, 없으면 AI 가 알려 준 값 |

| 실패 | `reason` | 상태 | `field` |
|---|---|---|---|
| 사진이 아니거나, 형식·크기가 안 맞거나, 두 장 이상이거나, 안 보냄 | `photo_invalid` | 422 | `image` |
| AI 가 응답하지 못함 (대기 시간 초과, 오류, 응답 모양 불량) | `ai_failed` | 502 | `null` |
| 저장 실패 | `server_error` | 500 | `null` |

- 신선식품이 하나도 없거나 읽지 못한 것은 실패가 아니다. `items` 가 빈 목록이고 `analysis_id` 가 `null` 이다. 화면이 안내와 직접 등록으로 가는 길을 보인다. (US-017, US-018)
- 사진 읽기의 응답에는 사진도, 영수증에 적힌 글 전체도 담지 않는다. 식품 이름과 보관 정보뿐이다. (D-102)
- 이 창구는 식품도 규칙표도 바꾸지 않는다. 규칙표에 더하는 일은 F2 에서 등록을 확정할 때 한다. (D-136)
- 규칙표에 같은 이름이 있으면 AI 가 준 위험 여부 · 이유 · 종류는 쓰지 않고 규칙표 값을 돌려준다(`from_rule` 이 참). 규칙표에 없고 AI 가 위험 여부를 알려 주지 않은 줄은 목록에서 빠진다. (V-36, D-190, D-191)

#### F2. 한꺼번에 등록 — `POST /foods/bulk` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | `analysis_id` 와 `items`. `items` 는 줄마다 `item_no`, `name`, `quantity`, `unit`, `purchase_date`, `storage`(사용자가 확인·고친 값) ✅ (ARCHITECTURE 3절). 확인 화면에서 **이름을 고쳐 규칙표에 없게 된 줄**은 `expiry_date`(날짜) **또는** `expiry_in_days`(며칠 뒤) 중 하나를 더 보낸다 |
| 하는 일 | 한 묶음(V-25)으로 ① 로그인·분석 번호 확인(내 것, 30분 안, V-31) → ② 줄마다 검사(V-24) → ③ 줄마다 기한 계산 → ④ 규칙표에 없는 이름을 규칙표에 더함 → ⑤ 식품 저장 → ⑥ 쓴 분석 결과 지움. 하나라도 실패하면 **전부 취소** (D-110) |
| 성공 | **201**, `{ "items": [식품 한 건, ...] }` — 보낸 줄 순서대로, 0-1절 모양 |
| 실패 | 아래 표 |
| 근거 | US-019, US-020, D-108 ~ D-111, D-133 ~ D-136, D-165, D-190, D-191, 시나리오 9 |

**줄 종류별로 하는 일**

| 줄 | 하는 일 | 근거 |
|---|---|---|
| AI 가 읽은 이름 그대로이고 규칙표에 이미 있음 | 규칙표 값으로 기한 계산, `source` = `rule` 로 저장 | D-134, D-135 |
| AI 가 읽은 이름 그대로이고 규칙표에 없음 | **서버가 보관한 AI 결과**의 보관 정보 · **위험 여부 · 이유 · 식품 종류**를 규칙표에 더하고(V-26, V-36), 그 값으로 기한 계산, `source` = `rule` 로 저장. 화면이 보낸 값은 규칙표에 쓰지 않는다 | D-133, D-134, D-136 |
| 이름을 고쳤고 고친 이름이 규칙표에 있음 (이름 또는 별칭) | 규칙표 값으로 기한 계산, `source` = `rule` | D-135, ARCH 9절 26번 |
| 이름을 고쳤고 규칙표에 없음 | 규칙표에 더하지 않는다. 함께 보낸 `expiry_date` 또는 `expiry_in_days` 로 기한을 정하고 `source` = `manual` 로 저장. `category` 는 서버가 보관한 결과에서 이 줄(`item_no`)의 AI 가 읽은 종류를 쓴다. 위험 표시는 붙지 않는다 | ARCH 9절 25번, D-166, 5절 50번 |

**실패** — 첫 오류 하나만 돌려주고, `field` 에 줄 위치를 넣는다 (`items.N.칸이름`, N 은 보낸 `items` 목록에서 줄의 위치, 0부터). **어떤 오류를 먼저 돌려줄지**는 이 순서다: 요청 전체(`items` 가 비었음, `analysis_id`) → 줄 순서대로(위에서 아래) → 한 줄 안에서는 이름, 단위, 수량, 구매일, 보관 방법, 기한 순

| 실패 | `reason` | 상태 | `field` |
|---|---|---|---|
| `items` 가 비었음 | `required` | 422 | `items` |
| `analysis_id` 가 내 것이 아님 · 없음 · 30분이 지남 | `analysis_expired` | 422 | `null` |
| 줄의 `item_no` 가 분석 결과에 없거나 두 번 나옴 | `invalid_item` | 422 | `items.N.item_no` |
| 이름 · 단위가 비었음 | `required` | 422 | `items.N.name` 또는 `items.N.unit` |
| 수량 오류 | `invalid_quantity` | 422 | `items.N.quantity` |
| 구매일이 올바른 날짜가 아님 | `invalid_date` | 422 | `items.N.purchase_date` |
| `storage` 가 세 값 중 하나가 아님 | `invalid_storage` | 422 | `items.N.storage` |
| 그 식품에서 "불가"인 보관 방법 | `storage_not_allowed` | 422 | `items.N.storage` |
| 이름을 고쳐 규칙표에 없게 됐는데 기한을 안 보냈거나 둘 다 보냄 | `expiry_input_invalid` | 422 | `items.N.expiry_date` |
| 적은 기한이 오늘보다 과거 | `expiry_in_past` | 422 | `items.N.expiry_date` |
| 기한이 구매일보다 앞 | `purchase_after_expiry` | 422 | `items.N.expiry_date` |
| `expiry_in_days` 가 정수가 아니거나 음수 | `invalid_expiry_in_days` | 422 | `items.N.expiry_in_days` |
| 저장 실패 (일부만 실패해도 전부 취소) | `server_error` | 500 | `null` |

- 같은 이름의 줄이 여러 개여도 따로 등록한다. (D-030)
- 요청 칸은 이전과 같다. 위험 여부 · 이유 · 종류는 화면이 보내지 않고 서버가 보관한 AI 결과에서만 가져온다. 응답의 식품 한 건에는 `is_danger`, `danger_note`, `category` 가 붙는다. (D-136, D-165)
- 같은 이름을 두 계정이 동시에 규칙표에 더하려 하면 먼저 저장된 것이 남고, 나중 요청은 그 값을 쓴다. 등록 전체는 취소하지 않는다. (ARCH 4-3)
- 사진으로 읽은 식품이 아니어도 이 창구로 등록할 수 있는지는 정하지 않았다. 분석 번호 없이는 부르지 못한다. (5절 31번)
- 화면은 줄마다 미리 검사하므로(D-108) 이 오류는 화면을 거치지 않은 요청에서 주로 난다. (D-010)

### 2-6. 음식 추천 (US-021, US-022)

#### G1. 음식 추천 — `POST /recommendations` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | `meal`(`breakfast` · `lunch` · `dinner`), `cuisine`(`western` · `korean` · `japanese` · `chinese` · `simple` · `custom`), `cuisine_text`(`cuisine` 이 `custom` 일 때만, **30자까지**) ✅ (ARCHITECTURE 3절, 글자 수는 사용자 결정) |
| 하는 일 | **내 식품 중 처리 상태가 `none` 이고 지남이 아닌 것**을 읽는다(V-12, D-120). 하나도 없으면 AI 를 부르지 않고 빈 목록을 돌려준다. 있으면 식품 이름과 남은 날, 끼니와 음식 종류를 AI 에게 보내 음식을 받는다(30초까지 기다림). 응답을 검사해 **내 식품이 재료로 2개 이상** 들어가는 음식만 남기고(D-119) 3개 이하로 자르고(D-113) **기한이 임박한 식품을 먼저 쓰는 음식**이 앞에 오게 정렬한다(D-114). 재료마다 가진 식품인지 표시한다(D-115). **저장하지 않는다** (D-122) |
| 성공 | **200**. 아래 모양 ✅ (ARCHITECTURE 3절) |
| 실패 | 아래 표 |
| 근거 | US-021, D-113 ~ D-123, D-131, 시나리오 17 |

```
{
  "dishes": [
    {
      "name": "김치볶음밥",
      "ingredients": [
        { "name": "김치",   "have": true },
        { "name": "달걀",   "have": true },
        { "name": "참기름", "have": false }
      ]
    }
  ],
  "reason": null
}
```

| 칸 | 값 | 뜻 |
|---|---|---|
| `dishes` | 목록 (최대 3개) | 추천한 음식. 음식 이름과 재료만 있고 만드는 법은 없다 (D-121) |
| `dishes[].ingredients[].have` | `true` / `false` | 내 식품이면 `true`, 지금 없는 재료면 `false` |
| `reason` | `null` / `no_foods` / `no_match` | `dishes` 가 비었을 때만 채운다. 가진 식품이 없으면 `no_foods`, 재료가 2개 이상 들어가는 음식을 찾지 못하면 `no_match`. 오류의 `reason` 이 아니라 성공 응답의 칸이다 |

| 실패 | `reason` | 상태 | `field` |
|---|---|---|---|
| `meal` 이 세 값 중 하나가 아니거나 없음 | `invalid_meal` | 422 | `meal` |
| `cuisine` 이 여섯 값 중 하나가 아니거나 없음 | `invalid_cuisine` | 422 | `cuisine` |
| `cuisine` 이 `custom` 인데 `cuisine_text` 가 비었거나 30자를 넘음 | `invalid_cuisine_text` | 422 | `cuisine_text` |
| AI 가 응답하지 못함 | `ai_failed` | 502 | `null` |
| 불러오기 실패 | `server_error` | 500 | `null` |

- `cuisine` 이 `custom` 이 아닌데 `cuisine_text` 가 함께 오면 무시한다. (A5 의 `expiry_date` 와 같은 이유)
- 같은 요청을 다시 보내면 새 추천이 나온다. 횟수 제한은 없다. (D-123)
- 가진 식품이 없거나 맞는 음식이 없는 것은 실패가 아니다. 화면이 안내를 보인다. (US-021, SCREEN-SPEC 8.4)

### 2-7. 계정 탈퇴 (US-025)

#### H1. 탈퇴 — `POST /account/withdraw` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | `password` ✅ (ARCHITECTURE 3절) |
| 하는 일 | 비밀번호가 맞는지 확인한다(V-29). 맞으면 한 묶음으로 **이 계정의 식품(처리한 식품 포함), 사진 읽기 결과, 모든 기기의 로그인 상태, 계정**을 지운다. 하나라도 실패하면 전부 취소해 아무것도 지워지지 않는다 (D-127, D-129) |
| 성공 | **204**, 본문 없음. 이 기기의 쿠키도 끝난다. 화면은 로그인 화면으로 간다 |
| 실패 | 비밀번호가 틀리거나 비었음 `password_mismatch` 422 (`field` = `password`) / 삭제 실패 `server_error` 500 |
| 근거 | US-025, D-089, D-127 ~ D-129, 시나리오 19 |

- 사진 등록으로 규칙표에 더해진 식품 정보는 탈퇴해도 지우지 않는다. 누가 더했는지 기록하지 않는다. (ARCH 4-3)
- 탈퇴한 이메일로 다시 가입하면 새 계정이다. (US-025)
- 화면은 확인 창에서 비밀번호를 적고 확인한 뒤에만 이 창구를 부른다. (D-128, SCREEN-SPEC 9.4)

### 2-9. 기록 조언 (US-034)

#### I1. 기록 조언 — `POST /advice` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | 없음 ✅ (ARCHITECTURE 3절) |
| 하는 일 | **내 식품**(처리 전 + 처리한 식품)을 읽는다. 하나도 없으면 AI 를 부르지 않고 `no_data` 로 돌려준다(V-37). 있으면 처리 전 식품의 이름 · 상태 · 남은 날, 처리한 식품의 이름 · 처리 종류 · 처리한 날짜 · 기한을 AI 에게 보내 기록과 지금 상태를 함께 본 조언을 받는다(30초까지 기다림). 응답 모양(글 목록이고 비어 있지 않음)을 검사해 돌려준다. **저장하지 않는다** (D-161) |
| 성공 | **200**. 아래 모양 ✅ |
| 실패 | 아래 표 |
| 근거 | US-034, D-159 ~ D-163, D-131, D-132, ARCHITECTURE 3-1, 7-16 |

```
{
  "advice": [ "조언 글", "조언 글" ],
  "reason": null
}
```

| 칸 | 값 | 뜻 |
|---|---|---|
| `advice` | 글자의 목록 | 조언 글. 식품도 기록도 없으면 빈 목록 |
| `reason` | `null` / `no_data` | `advice` 가 빌 때만 `no_data`. 오류의 `reason` 이 아니라 성공 응답의 칸이다 |

| 실패 | `reason` | 상태 | `field` |
|---|---|---|---|
| AI 가 응답하지 못함 (30초 초과, 오류, 답 모양 불량) | `ai_failed` | 502 | `null` |
| 불러오기 실패 | `server_error` | 500 | `null` |

- 식품도 처리한 기록도 없는 것은 실패가 아니다. 화면이 안내와 등록 버튼을 보인다. (D-162)
- AI 에는 식품 이름 · 상태 · 처리 종류 · 날짜만 보낸다. 이메일 · 계정 번호 · 수량 · 구매일은 보내지 않는다. (D-163)
- 같은 요청을 다시 보내면 새 조언이 나온다. 횟수 제한은 없다. (D-123)
- 화면은 받는 동안 '조언 받기' 버튼을 흐리게 하고 다시 보내지 않는다. 확인 중 화면은 없다. (0절, SCREEN-SPEC 7.6)

### 2-10. 오늘의 일반 조언 (US-033, US-043)

#### J1. 오늘의 일반 조언 — `GET /tips` 🔒

| 항목 | 내용 |
|---|---|
| 보내는 칸 | 없음 ✅ (ARCHITECTURE 3절) |
| 하는 일 | 오늘(서버 한국 시간)의 일반 냉장고 · 식품 관리 조언이 저장돼 있으면 그대로 돌려준다. 없으면 **이 요청이** AI 에게 만들게 하고(30초까지 기다림), 모양을 검사해 맞는 문장만 오늘 날짜로 저장한 뒤 돌려준다. AI 가 못 만들거나 하나도 남지 않으면 **저장하지 않고 미리 써 둔 조언**을 돌려준다(다음 요청에서 다시 만들어 본다). 모든 계정이 같은 조언을 읽는다 (D-156, D-157) |
| 성공 | **200**. 아래 모양 ✅ |
| 실패 | 아래 표 |
| 근거 | US-033, US-043, D-153 ~ D-158, ARCHITECTURE 3-1, 7-17 |

```
{
  "tip_date": "2026-11-04",
  "tips": [
    { "text": "냉장고 문 쪽은 온도가 자주 변해요. 우유는 안쪽에 두세요.", "from_ai": true }
  ]
}
```

| 칸 | 값 | 뜻 |
|---|---|---|
| `tip_date` | 날짜 글자 | 오늘(한국 시간). 화면은 이 날짜를 따로 쓰지 않는다 |
| `tips[].text` | 글자 | 조언 한 문장 |
| `tips[].from_ai` | `true` / `false` | AI 가 만든 것이면 `true`, 미리 써 둔 것이면 `false` |

| 실패 | `reason` | 상태 | `field` |
|---|---|---|---|
| 저장된 조언을 읽지 못함 · 저장 실패 | `server_error` | 500 | `null` |

- AI 가 응답하지 못해도 `ai_failed` 를 주지 않는다. 미리 써 둔 조언이 대신 나가서 사용자에게 실패가 보이지 않는다. (D-157)
- 화면은 사진 읽기(F1) · 음식 추천(G1)을 보낼 때 이 창구도 함께 부른다. 조언 중 하나를 안내 한 줄 아래에 보이고, 확인 중 화면을 열 때마다 다른 조언을 보인다. 조언 개수는 구현 단계에서 정한다. (ARCHITECTURE 7-17)
- 이 창구가 실패하면 확인 중 화면의 조언 칸만 비고, 사진 읽기 · 음식 추천은 계속된다. (5절 53번)
- 개인 정보를 AI 에 보내지 않는다. 요청만 보낸다. (ARCHITECTURE 3-1)

## 4. 하지 말 것

기준 문서에 근거가 없거나 범위 밖인 것은 이 문서에서 정하지 않는다. 필요해지면 DECISIONS 에 먼저 적고 다시 넣는다.

| 하지 않는 것 | 이유 |
|---|---|
| 내 로그인 상태를 묻는 창구(`GET /auth/me` 등) | ARCHITECTURE 3절의 창구 목록에 없다. 앱을 켤 때는 홈 목록(A1)이 401 인지로 로그인 여부를 안다 |
| 비밀번호 찾기·변경, 이메일 인증, 소셜 로그인, 로그인 틀림 횟수 제한 | D-048 ~ D-051 |
| 사진 저장, 사진을 다시 내려받는 창구 | 올린 사진은 저장하지 않는다 (D-102) |
| 음식 추천 결과를 저장·다시 보는 창구, 음식의 만드는 법 | 결과는 저장하지 않고 이름과 재료만 보여 준다 (D-121, D-122) |
| 규칙표를 직접 고치는 창구, 화면이 보낸 값을 규칙표에 쓰는 일 | 규칙표는 개발자와, 사진 읽기 결과로만 채워진다 (D-133, D-136). 직접 등록 식품은 규칙표에 더하지 않는다 (D-091) |
| 사진 여러 장을 한 번에 읽기 | 한 번에 한 장 (D-101) |
| AI 사용 횟수 제한 | 제한하지 않는다 (D-123) |
| 알림, 기한 기준 조절, 홈 화면에 앱처럼 추가 | R-009, R-018, R-019 (PRD 5절). 위험 식품 표시는 이번 버전에 들어왔다 (R-043) |
| 가족 맺기, 가족 냉장고 | Later (R-016, R-017) |
| 같은 요청이 두 번 왔는지 서버가 가려내기 | 같은 이름의 식품을 여러 건 등록할 수 있어서 서버가 "연타"와 "일부러 한 번 더"를 구별할 수 없다. 화면이 누르는 순간 막는다 (D-030, D-099, D-112) |
| 식품 목록을 쪼개 보내는 쪽수 나누기(페이지) | 목록 개수에 제한을 두지 않는다 (D-025) |
| 식품 응답에 보관 방법별 가능 여부를 담기 | 규칙표 검색 결과로 풀기로 했다 (SCREEN-SPEC 13.1 의 8번) |
| 기존 식품 옮기기를 직접 부르는 창구 | 첫 가입·첫 계정의 로그인 안에서 자동으로 한다 (D-042, D-096) |
| 기존 식품을 옮긴 뒤 SQLite 를 읽거나 쓰기 | SQLite 는 폐기했다. 파일은 백업으로만 남긴다 (D-038, D-097) |
| 보관 방법만 바꾸는 별도 창구 | 정보 고치기(A5)로 합쳤다 (ARCHITECTURE 9절 34번) |
| 색(밝기·포인트 색)을 읽거나 저장하는 창구, 계정 정보 보기 창구 | 색은 이 기기에만 저장한다 (ARCHITECTURE 9절 36번, SCREEN-SPEC 9.5) |
| 상태 알약 · 드롭다운 · 막대 달력 주 넘기기 · 전체 달력만을 위한 새 창구 | 화면이 홈 목록(A1) 하나로 한다 (ARCHITECTURE 9절 31번) |
| 기록 조언의 저장 · 다시 보기, 조언 횟수 제한 | 저장하지 않고 횟수 제한도 없다 (D-161, D-123) |
| 일반 조언을 계정마다 따로 만들기, 사용자가 일반 조언을 고치기 | 하루 한 번 모든 계정이 같은 것을 읽는다 (D-156) |
| 위험 여부 · 위험 이유를 사용자가 고치는 창구 | 규칙표 값을 따르고 직접 등록 식품은 위험 표시가 없다 (D-164, D-166) |

## 5. 정한 것

기준 문서에 답이 없어서 정한 것이다. **사용자가 정한 것**과 **이 문서에서 정한 것(확인 필요)** 을 구분해 적었다.

| # | 항목 | 정한 내용 | 이유 | 영향 | 정한 사람 |
|---|---|---|---|---|---|
| 1 | 이유 이름 | 3절 표의 이름을 그대로 쓴다 | 화면이 이름으로 안내를 붙일 칸을 정하므로, 이름 하나가 한 가지 일만 뜻해야 구분하기 쉽다 | 전체 | 사용자 |
| 2 | 성공 상태 번호 | 만들기 201(한꺼번에 등록 포함), 삭제·로그아웃·탈퇴 204, 나머지(사진 읽기·음식 추천 포함) 200 | 삭제 204 가 이미 정해져 있어서, 만들기와 나머지를 일반적인 규칙에 맞춘다. 사진 읽기와 음식 추천은 만드는 일이 아니라 결과를 돌려주는 일이다 | 전체 | 사용자 |
| 3 | 응답 칸 이름 | 홈 목록 `{today, items}`, 규칙표 검색 `{items:[{name, default_storage, disallowed_storages}]}`, 기록 숫자 D1 의 JSON, 처리한 식품 목록 `{eaten, discarded}`, 가입·로그인 `{email}` | 화면과 API 가 같은 이름을 써야 하고, 홈 목록은 `today` 를 함께 줘야 해서 감싼다 (D-021) | A1, C1, B1, B2, D1, D2 | 사용자 |
