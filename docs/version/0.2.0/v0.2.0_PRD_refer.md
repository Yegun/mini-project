# PRD 작성 참고 (교재 기준)

> 교재 `MZC-AICAMP-M3-VC-Day7-Workbook-v1.2`의 내용만 정리했다. 교재의 "Task 앱"은 예시이므로 "내 앱"으로 바꿔 적었다.

## 1. PRD를 대하는 마음가짐

- **PRD는 약속 문서다.** 화면을 예쁘게 만드는 문서가 아니다. 누구의 어떤 문제를, 첫 버전에서 어디까지, 어떻게 되면 "끝"으로 볼지 적는다.
- **AI는 초안을 쓰고, 결정은 사람이 한다.** AI가 제안한 기능과 내가 만들기로 한 기능은 다르다. AI의 말이 그럴듯해도 확정이 아니다.
- **모르면 모른다고 한다.** 모르는 채로 억지로 고르지 않는다. AI에게 쉬운 설명, 후보 2개 이상, 비교, 추천을 요청한다. 최종 선택은 내가 한다.
- **지어내지 않는다.** 실제 사용자 조사를 하지 않았다면 "사용자가 ~를 원한다"고 쓰지 않고 "가정"이라고 쓴다. 고객 조사를 한 것처럼 쓰면 안 된다.
- **천천히 하는 게 맞다.** 느려 보여도 각 단계에서 무엇을 확인하는지 알아야, 나중에 잘못된 가정이 어디서 들어왔는지 찾을 수 있다.

## 2. 무엇을, 어떻게 (순서)

| 단계 | 무엇을 | 어떻게 |
|---|---|---|
| ① 아이디어 전달 | 한 문장으로 만들고 싶은 것과 고정 조건을 말함 | AI에게 방향 문서(DECISIONS.md)를 주고 "모르는 건 임의로 확정하지 말고, 질문은 한 번에 하나씩 하라"고 요청 |
| ② 요구사항 후보 받기 | R-001, R-002처럼 번호 붙은 후보 | 후보마다 기능, 필요한 이유, 내가 답할 질문을 나누게 함. 상태는 "검토 필요", Must로 확정 금지, 내가 말하지 않은 건 "AI 제안"으로 표시 |
| ③ 항목별 판정 | 후보마다 수락 / 수정 / 제외 / 설명 필요 / 보류 | 각각 이유를 함께 말함. 모르는 건 "설명 필요"로 물어봄 |
| ④ 승인한 것만 반영 | 판정한 결정만 PRD의 요구사항 후보에 적음 | "아래 결정만 반영, 기존 ID 유지, 수락 안 한 건 확정 문장으로 바꾸지 말 것, 바꾼 것과 안 바꾼 것을 나눠 보고"라고 지시 |
| ⑤ 대화와 파일 비교 | 대화에서 정한 것과 파일이 같은지 | 사람이 직접 파일을 열어 확인 |
| ⑥ 발견 종료 조건 점검 | 체크리스트 10개 통과 | 5번 참고 |
| ⑦ PRD v0.1 작성 | 수락 또는 수정된 후보만 사용 | 주요 문장마다 요구사항 ID나 결정 ID를 붙임 |
| ⑧ AI에게 검토시킴 | 빠진 것, 충돌, 모호한 곳 찾기 | "대신 다시 쓰지 말고 표로 보고만" 하게 함. 제안은 전부 받지 않고 수락, 수정, 보류, 거절과 이유를 기록 |
| ⑨ 확정 | 상태를 "확정"으로 표시 | 결정자, 승인일, 기준 문서, 남은 열린 질문을 함께 적음 |

## 3. 결과물은 이래야 한다

### PRD에 들어갈 10가지

| 항목 | 답해야 할 질문 |
|---|---|
| 한 문장 설명 | 누구의 어떤 일을 어떻게 돕는가? |
| 사용자와 상황 | 누가, 언제 쓰는가? |
| 문제와 영향 | 무엇이 반복해서 불편하고, 어떤 손실이 생기는가? |
| 목표 | 이번 버전에서 무엇이 달라져야 하는가? |
| 성공 확인 | 무엇을 보면 목표 달성을 알 수 있는가? |
| 범위와 비범위 | 지금 만들 것과 만들지 않을 것은? |
| 사용자 스토리 | 어떤 목적으로 어떤 행동을 원하는가? |
| 완료 조건 | 어떤 결과가 보이면 "완료"인가? |
| 비기능 요구사항 | 보안, 접근성, 오류, 저장 유지에서 지킬 것은? |
| 가정과 질문 | 아직 확인 못 한 것은? |

### 글 쓰는 규칙

1. **한 문장 설명**에는 사용자, 문제, 가치가 모두 보여야 한다. "OO를 관리하는 웹 앱이다"는 부족하다.
2. **목표와 기능을 구분한다.** 목표는 "사용자에게 생겨야 할 변화", 기능은 "그 변화를 위해 시스템이 제공하는 것"이다.
3. **사용자 스토리**는 "[사용자]로서 [목적]을 위해 [행동]하고 싶다" 형식으로 쓴다. "React 컴포넌트를 만든다" 같은 구현 방법은 쓰지 않는다.
4. **완료 조건**은 네 상황으로 나눈다. 각각 사용자의 행동과 화면에서 볼 결과가 함께 있어야 한다.
   - 정상: 올바르게 입력하면 무엇이 보이는가
   - 빈 결과: 데이터가 없으면 무엇이 보이는가
   - 잘못된 입력: 허용하지 않는 값을 넣으면 무엇이 보이는가
   - 실패: 저장이나 서버가 실패하면 어떻게 알 수 있는가
5. **우선순위**를 나눈다.
   - Must: 이게 없으면 대표 사용 흐름을 끝낼 수 없음
   - Later: 방향은 맞지만 첫 구현 뒤로 미룰 수 있음
   - 비범위: 넣으면 다른 제품이나 큰 프로젝트가 됨

   AI가 전부 Must로 넣으면 핵심 흐름만 남겨 다시 분류시킨다. "있으면 좋아 보인다"는 이유로 Must에 넣지 않는다.
6. **네 가지를 섞지 않는다.**
   - 확인한 사실: 문서, 관찰, 직접 확인으로 안 것
   - 가정: 확인은 안 했지만 임시로 둔 판단 (반드시 "가정"이라고 표시)
   - 열린 질문: 결정 전에 더 알아야 하는 것
   - 결정: 이유를 검토해 적용하기로 한 것
7. 확인된 내용은 평서문으로 쓴다. 기능 이름만 나열하지 않고 사용자의 행동과 결과를 연결해서 쓴다.
8. 비기능은 근거 없는 성능 숫자를 만들지 않고, 현재 상황에서 확인 가능한 조건만 적는다.

### 문서 간 역할

| 문서 | 담는 것 |
|---|---|
| DECISIONS.md | 내가 확정한 결정만 (번호, 내용, 이유, 적용 범위, 관련 문서, 유효 상태). 후보나 승인 대기는 넣지 않음 |
| PRD.md | 요구사항 후보, 열린 질문, 판정, 확정된 요구 |
| PLAN.md | 작업 순서, 상태, 실제 검증 결과 |

## 4. 사람이 해야 하는 일

- 모든 후보를 직접 판정한다. AI의 "수락하세요"를 따라가지 않는다.
- AI의 "반영했습니다"라는 보고만 믿지 않고, **실제 파일을 열어** 확인한다.
  - 수락한 요구가 PRD에 들어갔는가
  - 수정한 요구가 수정 전 문장으로 돌아가지 않았는가
  - 제외한 요구가 Must나 사용자 스토리에 들어가지 않았는가
  - 보류한 요구가 확정 기능처럼 적히지 않았는가
- 요구사항 ID가 없는 문장은 AI가 새로 만들었을 수 있으니 근거를 확인한다.
- AI가 임의로 확정하거나 구현으로 넘어가면 멈추고, 어디가 잘못됐는지 짚어서 다시 요청한다.
- 결정할 때는 이유를 같이 남긴다.

## 5. 확정해도 되는지 확인하는 기준

### 발견 종료 조건 10개

이걸 통과하기 전에는 이번 범위를 확정하지 않는다.

- [ ] 대상 사용자와 상황을 내 말로 설명할 수 있다
- [ ] 해결할 문제와 현재 불편을 설명할 수 있다
- [ ] 카드(핵심 대상)의 필드 후보를 모두 판정했다
- [ ] 상태 이름과 변경 규칙을 정했거나 보류 이유를 적었다
- [ ] Must, Later, 제외 범위를 구분했다
- [ ] 정상, 빈 결과, 잘못된 입력, 실패의 후보가 있다
- [ ] 사실, 가정, 열린 질문이 섞이지 않았다
- [ ] 모든 후보에 ID와 판정이 있다
- [ ] 대화에서 승인한 것과 PRD가 일치한다
- [ ] 구현을 막는 열린 질문이 없다

### 확정 전에 내 말로 답할 6가지

1. 대상 사용자는 누구인가?
2. 핵심 문제는 무엇인가?
3. Must의 대표 흐름은 무엇인가?
4. 첫 버전에서 하지 않는 일은 무엇인가?
5. 모든 주요 문장을 어떤 요구사항 ID로 설명할 수 있는가?
6. 어떤 가정이 남았고, 언제 다시 확인할 것인가?

설명이 안 되면 그 PRD 문장은 아직 내 결정이 아니다.

## 6. 왜 이렇게 하라는 건가 (교재의 설명)

- AI는 앞의 조건을 잊거나, 고르지 않은 걸 고른 것처럼 쓸 수 있다. 그래서 **결정은 대화가 아니라 기록(파일)** 으로 남긴다.
- PRD는 구현 중에 새 아이디어가 나왔을 때 "지금 넣을지, 나중으로 미룰지" 판단하는 기준이다.
- 열린 질문 중 **이번 구현을 막는 것**만 먼저 해결하고, 이후 기능 질문은 보류 범위로 표시해서 이번 PRD에 섞지 않는다.
- 확정은 "이번 구현의 기준"이라는 뜻이지 영구히 못 바꾼다는 뜻이 아니다. 요구가 바뀌면 영향을 확인하고 승인한 뒤 관련 문서를 같이 고친다. 이전 결정은 지우지 않고 새 번호로 대체 관계를 남긴다.
- 읽는 중에 내용을 세 가지로 표시한다.
  - 고정: 바꾸지 않는 조건
  - 선택: 대안을 비교한 뒤 사람이 정할 것
  - 질문: 아직 몰라서 확인이 필요한 것

  AI가 고정 조건을 대안으로 바꾸거나, 질문을 사실처럼 채우면 멈추고 바로잡는다.

## 7. 이 프로젝트의 두 파일과 연결해서 볼 점

- **PRODUCT-DIRECTION.md**는 교재의 DECISIONS.md(고정 조건과 확정 방향)에 가깝다.
- **PROJECT-DISCOVERY.md**는 교재의 "요구사항 후보 + 판정 + 열린 질문" 단계에 가깝다.

PRD v0.1은 이 두 파일에서 **"수락 또는 수정"으로 판정된 항목만** 가져와 쓴다. 먼저 AI에게 "사용한 ID와 제외한 ID를 보고한 뒤 초안을 작성하라"고 시킨다.
