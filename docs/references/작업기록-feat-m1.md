# feat/m1 브랜치 작업 기록

## 들어가며

`feat/m1` 은 문서 작업(`docs/m1`)이 끝난 다음 단계, 즉 **프론트엔드(화면)·백엔드(서버)·DB(저장소)를 실제로 만든 작업을 한곳에 모은 브랜치**다. 세 사람이 각자 `feat/m1-frontend`, `feat/m1-backend`, `feat/m1-database` 라는 작은 브랜치에서 일하고, 그 결과가 Pull Request(합치기 요청)로 이 브랜치에 차례로 합쳐졌다. 그래서 이 브랜치의 기록을 보면 "세 영역이 동시에 어떻게 만들어지고 어떻게 맞춰졌는지"를 볼 수 있다.

이 기록이 다루는 구간은 2026년 10월 30일 오후 3시 31분부터 오후 5시 37분까지다. 앞 구간(`docs/m1`, 끝 지점 `77bafd6`)은 [작업기록-docs-m1.md](작업기록-docs-m1.md)에 따로 적었다. 이 브랜치의 끝 지점은 `67a18ed`(PR #16 병합)이다.

### 식품 등록 화면 (`5c2554f`, 10-30 16:52)

22개 파일, 약 1,850줄을 한 번에 올렸다. 등록 방법이 두 가지라서 화면도 두 흐름이다.

- **규칙표에서 골라 등록**: 이름을 검색해서(`RuleSearch`) 후보를 고르고(`RuleRegisterForm`), 보관 방법(`StoragePicker`)과 수량·단위·구매일(`QuantityUnitDateFields`)을 적는다. 기한은 서버가 계산하므로 입력받지 않는다. 사용할 수 없는 보관 방법은 흐리게 보여 주고 고를 수 없게 한다(D-005).
- **직접 등록**: 규칙표에 없는 식품을 위한 화면(`ManualRegisterForm`)이다. 기한은 날짜로 고르거나 "며칠 뒤"로 적는다.
- 그 밖에 검사 규칙(`lib/registerForm.ts`), 날짜 글자 처리(`lib/dateText.ts`), 가짜 규칙표 데이터(`mocks/rules.json`, 676줄), 등록한 식품을 홈 가짜 목록에 합치는 장치(`mocks/createdFoods.ts`)를 넣었다.

### 식품 상세 화면 (`104d1cf`, 10-30 17:12)

19개 파일, 약 1,000줄이다. 상세 화면은 식품 하나를 보고 고치는 화면이다.

- **요약**(`FoodSummary`): 이름, 보관 방법, 구매일, 기한과 상태.
- **정보 고치기**(`InfoEditForm`): 이름·구매일·수량·단위를 고친다. 이름을 규칙표에 없는 이름으로 바꾸면 **기한 다시 적기** 칸(`ExpiryRewriteField`)이 열린다(D-023).
- **보관 방법 바꾸기**(`StorageChangeForm`).
- **확인 창**(`ConfirmDialog`): 다 먹음·버림·삭제를 누를 때 한 번 더 묻는다.
- 요청·응답 모양(`types/foodDetail.ts`, `api/foodDetail.ts`), 불러오는 부분(`hooks/useFoodDetail.ts`), 입력 검사(`lib/editForm.ts`), 가짜 상세 데이터(`mocks/foodDetails.json`)를 함께 만들었다.
- 저장·처리·삭제가 성공하면 홈으로 돌아간다(D-020). 화면 전환은 주소가 아니라 상태값으로 한다(`App.tsx`).

### 가짜 데이터로 화면 확인하기

`frontend/.env.local` 에 `VITE_USE_MOCK` 값을 넣으면 화면이 서버 없이도 돈다(이 파일은 Git에 올리지 않는다). 값에 따라 식품 있음(`1`), 식품 없음(`empty`), 불러오기 실패(`error`), 2초 늦게 응답(`slow`), 저장 실패(`save-error`), 입력 오류 응답(`save-invalid`) 등을 흉내 낸다. 같은 파일 설명에는 규칙 검색 실패(`rules-error`), 상세 불러오기 실패(`detail-error`)도 확인했다고 되어 있다.

### 화면 점검과 오류 수정 (10-30 17:23 ~ 17:26)

화면을 만든 뒤 점검해서 **오류 세 개**를 찾아 고쳤다. 점검 기록은 `docs/FRONTEND-ERRORS.md` 에 남겼다. 같은 문서에 따르면 `npm run build`, `npm run lint`, 타입 검사는 통과했고, 휴대폰 크기(375px, 320px) 화면에서 겹치거나 넘치는 곳이 없었다. 다만 **실제 휴대폰과 실제 서버로는 확인하지 못했다**고 적혀 있다.

| 오류 | 증상 | 원인 | 해결 | 커밋 |
|---|---|---|---|---|
| 1번 | 수량·단위만 고쳐도 "기한 다시 적기" 칸이 닫히고 적은 날짜가 지워졌다 | 어떤 칸이 바뀌어도 기한 칸을 닫고 비웠다 | 이름이나 구매일이 바뀐 경우에만 닫도록 조건을 넣었다 | `f8d64eb` |
| 2번 | 상세 아래쪽 버튼(삭제·다 먹음·버림)이 실패해도 알림이 맨 위에만 떠서 아무 반응이 없는 것처럼 보였다 | 알림을 띄우기만 하고 화면을 알림 위치로 옮기지 않았다 | 오류가 생기면 알림이 보이도록 스크롤한다 | `25373ac` |
| 3번 | 수량 `1` 을 `01` 로 고쳐 저장하면 바뀐 게 없는데 저장 버튼이 켜졌고, 누르면 아무것도 안 바뀐 채 홈으로 갔다 | 변경 여부 검사(글자 비교)와 요청 만들기(숫자 비교)가 서로 어긋났다 | 바뀐 칸이 없으면 요청을 보내지 않고, 입력칸을 저장된 값 모양으로 되돌린다 | `2820ff1` |

### 서버와 합칠 때 확인하기로 한 것

같은 문서의 "병합 시 확인" 절에 프론트엔드 담당이 **서버 쪽에서 맞춰 봐야 한다고 적어 둔 것**이 8가지 있다. 개발 서버가 `/api` 를 떼고 8000번 서버로 넘기는 설정(`frontend/vite.config.ts`), 입력 오류 응답 모양, "기한 다시 적기" 응답, 응답 칸 이름과 값, 오늘 날짜 형식, 정렬과 달력 제외는 서버 몫이라는 점, 없는 식품 요청의 오류 응답, 그리고 규칙표 30개 내용이 아직 가짜 값이라는 것이다.

## 2. 백엔드 (ANHYEONGCHEOL, PR #15)

### 무엇을 만들었나

API-SPEC에 약속한 **API 9개를 실제 서버로 구현**했다(`b8dc84c`, 10-30 16:10, 23개 파일, 약 2,600줄). 처음에는 DB 담당이 만든 부분을 쓰지 않고 자기 쪽에서 저장 부분까지 직접 만들었다. 이 부분은 뒤의 "4. 합친 뒤 고친 것"에서 정리된다.

### 서버의 구조

요청이 들어와서 답이 나가기까지 일을 층으로 나누었다. 각 층이 하는 일이 하나씩이라 고치기 쉽게 한 구조다.

1. **창구** (`backend/app/routers/foods.py`, `rules.py`): 화면이 보낸 요청을 받고 답을 돌려준다. 요청에 모르는 칸이 있으면 오류로 돌려준다.
2. **규칙 처리** (`services.py`): "규칙표에서 골라 등록하면 기한은 구매일 + 보관 일수", "보관 방법을 바꾸면 기한을 다시 계산"처럼 결정 문서의 규칙을 적용한다.
3. **계산·검사** (`calc.py`, `status.py`, `validation.py`): 날짜 계산, 상태 판정, 입력 검사. 한 곳에 모아 두어 여러 기능이 같이 쓴다.
4. **응답 만들기** (`view.py`): DB의 식품에 계산 값(`expiry_status`, `days_left`, `show_on_calendar`)을 붙여 화면이 받을 모양으로 만든다. 처리된 식품은 이 값이 비어(null) 있다.
5. **오류 틀** (`errors.py`): 오류는 항상 `field`(문제 칸), `reason`(이유), `message`(쉬운 문구) 세 칸이다. 입력 오류 422, 없는 식품 404, 기한 다시 적기 409, 저장·불러오기 실패 500이다(D-008).
6. **저장소 연결** (`database.py`): DB 파일을 열고, 요청 하나가 끝나면 저장하거나 실패하면 모두 되돌리는 장치(`transaction`)가 있다.

| A1 | 홈 목록 (오늘 날짜 + 식품 목록) | `GET /foods` |
| A2 | 규칙표 검색 | `GET /rules?q=` |

### 코드에 담은 결정

- **상태 판정**: 남은 날이 6일 이상이면 여유, 3~5일이면 주의, 0~2일이면 임박, 기한이 지났으면 지남이다. 기한이 4일 이상 지난 식품은 달력에서만 빠지고 목록에는 남는다(D-009, D-011, D-014).
- **정렬**: 기한이 빠른 순, 같으면 구매일이 이른 순, 그다음 이름순(D-015, D-033).
- **기한 계산**: "며칠 뒤"는 구매일 + N일(D-002). 구매일을 고치면 기한도 같은 일수만큼 옮긴다(D-024). 구매일이 미래라 보관한 기간이 음수면 0일로 계산한다(D-022). 보관 방법을 바꾸면 지난 정도를 새 방법 기준으로 환산한다(D-006).
- **그 밖**: 수량은 소수 둘째 자리까지(D-027), 이름·단위 글자 수는 제한하지 않음(D-025), 식품 번호는 UUID(D-033).

### 문서에 없어서 코드에서 정한 것

코드 주석과 코드로 확인되는 것만 적는다.

- 직접 등록(A4)에서 "며칠 뒤"를 보내는 칸 이름은 `expiry_in_days` 다.
- 다 먹음·버림(A8)은 `{"status": "eaten"}` 또는 `{"status": "discarded"}` 를 보낸다.
- 규칙표 검색(A2)은 검색어가 이름이나 별칭에 **들어 있으면** 찾는다. 이 방식은 이 브랜치에서 D-035로 문서에도 올랐다. 검색어가 비어 있으면 처음 구현에서는 오류(422)로 돌려주었고, 합친 뒤 고치는 과정에서 빈 목록으로 바뀌었다.
- 처음 구현에서는 처리된 식품에 다시 요청하면 409(이미 처리됨)로 돌려주었다. 합친 뒤 D-037에 맞춰 없는 식품과 똑같은 404로 바뀌었다.

## 3. DB (Yegun, PR #12·#13·#14)

### 무엇을 만들었나

식품 DB와 규칙표 DB를 **만들고, 읽고, 쓰는 부분**을 `backend/app/db/` 폴더에 만들었다(`63aa40c`, 10-30 15:31, 10개 파일, 약 700줄). SQLite를 쓰며 파일은 두 개다.

- 식품 DB: `backend/data/fridge.db`
- 규칙표 DB: `backend/data/rules.db`

환경 변수 `FRIDGE_DB_PATH`, `RULES_DB_PATH` 로 위치를 바꿀 수 있다. `*.db` 파일은 Git에 올라가지 않는다. 규칙표 DB는 읽기 전용으로 연다(D-007).

### 기본 원칙

`backend/app/db/README.md` 첫머리에 이렇게 적혀 있다. **"DB는 저장만 한다."** 기한 계산, 상태 판정, 오늘 날짜, 입력 검사 메시지, "불가" 보관 방법 거절은 모두 API가 한다. DB는 잘못된 값(수량 0 이하, 구매일이 기한보다 뒤, 이상한 날짜 등)이 들어오면 마지막으로 한 번 더 막기만 한다.

### 파일별 소개

| 파일 | 하는 일 |
|---|---|
| `schema.py` | 표를 만드는 문장. 식품 표 `foods`, 규칙표 DB의 `rules`(식품), `rule_aliases`(별칭), `rule_storage`(보관 방법별 가능 여부와 최대 보관 일수). 칸 이름과 값은 DATA-MODEL, D-032, D-034를 따른다. |
| `connection.py` | 파일 위치와 연결. 식품 DB는 읽고 쓰기, 규칙표 DB는 읽기 전용. |
| `foods_repo.py` | 식품 저장 함수 여섯 개: 만들기, 한 건 찾기, 목록, 수정, 처리(다 먹음·버림), 삭제. |
| `rules_repo.py` | 규칙표 읽기 함수: 검색(이름·별칭에 들어 있으면), 이름으로 찾기, 한 건, 전체. |
| `seed_rules.py` | 규칙표 30개 식품을 채우는 목록. 번호(UUID)는 이름에서 만들어서 다시 채워도 같다. |
| `init_db.py` | `python -m app.db.init_db` 한 줄로 DB를 만들고 규칙표를 채운다. 여러 번 실행해도 같은 결과이고 식품 데이터는 지우지 않는다. |
| `README.md` | 사용 설명서. API를 만드는 사람이 가져다 쓰는 용도. |
| `tests/test_db_foods.py`, `test_db_rules.py` | 두 영역의 시험. |

### 규칙표 값은 임시값이다

`seed_rules.py` 맨 위에 큼직하게 "임시값"이라고 적혀 있다. 식품 이름 30개는 확정이지만, 기본 보관 방법, 보관 가능 여부, 최대 보관 일수, 별칭은 식약처 자료로 확인한 값이 아니라 **일반 상식으로 적은 개발용 임시값**이다. 그래서 **화면에 보이는 기한 숫자는 믿지 않는다**는 것이 이 브랜치에서 정한 약속이다(D-036). 값이 확정되면 이 파일만 고치고 `init_db` 를 다시 돌리면 된다.

### 이 작업과 함께 올라간 결정

`2a34a7c`(10-30 15:32)에서 DECISIONS.md에 세 가지가 추가되었다.

- **D-035**: 규칙표 검색은 검색어가 이름이나 별칭에 들어 있으면 찾는다. (예: "양"을 치면 양파, 양배추)
- **D-036**: 규칙표의 이름 외 값은 개발용 임시값으로 먼저 채운다.
- **D-037**: 처리된(다 먹음·버림) 식품은 조회·수정·삭제가 모두 막히고, 없는 식품과 똑같이 취급한다.

## 4. 합친 뒤 고친 것 (`f649bdb`, Yegun, 10-30 17:33)

DB 담당 작업과 백엔드 작업이 합쳐지자, 같은 일을 하는 파일이 두 벌 생겼다. 이를 정리한 커밋이다. 18개 파일을 바꾸었고(456줄 추가, 454줄 삭제), 커밋 메시지는 "Backend, DB 병합 후 오류 수정"이다.

- **저장 담당을 하나로 합쳤다.** 백엔드가 처음 직접 만들었던 `repo_foods.py`, `repo_rules.py`(와 그 시험)를 지우고, DB 담당의 `app/db/foods_repo.py`, `rules_repo.py` 를 부르는 얇은 창구 `foods_store.py` 를 새로 만들었다. 이 창구는 DB의 날짜 글자(`2026-10-30`)와 서버 안의 날짜 값을 서로 바꿔 주는 일만 한다.
- **파일 위치를 한 곳에서만 정한다.** `database.py` 가 DB 파일 위치를 `app/db/connection.py` 에서 받아 쓰도록 바꿨다. 환경 변수 이름도 DB 담당 쪽(`FRIDGE_DB_PATH`)을 따른다. 연결이 칸 이름으로 읽을 수 있게(`row_factory`) 설정도 바꿨다.
- **규칙표 검색을 DB 쪽으로 옮겼다.** 서버에서 직접 찾던 부분을 DB의 `search_rules` 로 바꾸고, 검색어가 비어 있으면 오류 대신 빈 목록을 돌려주도록 했다(D-035).
- **처리된 식품은 "없는 식품"과 같은 오류(404)로 처리한다.** 이전의 "이미 처리됨(409)" 오류는 없앴다(D-037). 정렬도 DB 쪽에서 해서 서버에서 다시 정렬하는 부분을 지웠다.
- **규칙표를 고친 뒤 기한을 다시 계산하는 도구를 추가했다.** `app/db/recalc_expiry.py` 와 시험 `test_db_recalc.py`(185줄)다. 규칙표 값(`seed_rules.py`)을 고친 뒤에 개발자가 `python -m app.db.recalc_expiry` 를 한 번 실행하면, 이미 등록된 규칙표 식품의 기한을 새 값으로 다시 계산해 저장한다. `--dry-run` 을 붙이면 저장하지 않고 바뀔 내용만 보여 준다. 직접 등록한 식품과 처리된 식품은 건드리지 않는다. 앱이나 API에서는 부르지 않는다.
- 시험 파일 몇 곳(`conftest.py`, `test_api_*`, `test_real_files.py`)도 바뀐 이름에 맞게 고쳤다.

## 5. 영역끼리 맞춰야 하는 부분

프론트엔드와 백엔드는 따로 만들어서, 이 브랜치 끝(`67a18ed`)의 파일을 서로 비교해 보면 **약속이 다른 곳**이 있다. 아래는 양쪽 파일 본문에서 직접 확인한 것만 적었다. 합친 뒤 수정 커밋(`f649bdb`)은 프론트엔드 파일을 바꾸지 않았으므로, 이 브랜치의 끝에서도 이 차이가 남아 있다.

| 항목 | 프론트엔드가 쓰는 것 | 백엔드가 주는 것 |
|---|---|---|
| 상태 칸 이름 | `expiry_level` | `expiry_status` |
| 상태 값 | `relaxed` / `caution` / `urgent` / `expired` | `fresh` / `warning` / `soon` / `expired` |
| 규칙표 검색 결과 | 식품마다 `id`, `name`, `default_storage`, `storages`(방법별 가능 여부) | 식품마다 `name`, `default_storage`, `not_allowed`(쓸 수 없는 방법 목록). `id`와 `storages` 없음 |
| 규칙표 식품 등록 요청 | `rule_id` 를 함께 보냄 | 모르는 칸이 있으면 오류(422)로 돌려줌 |
| 직접 등록의 "며칠 뒤" | `expiry_days` | `expiry_in_days` |
| "기한 다시 적기" | 성공(200)에 `{status: "need_expiry"}` | 오류 409에 `reason: "expiry_required"` |
| 입력 오류 본문 | 422 + `{errors: {칸이름: 안내}}`, 기한 칸 이름은 `expiry` | `{field, reason, message}` 세 칸, 기한 칸 이름은 `expiry_date` |
| 상세 화면의 방법별 가능 여부 | 상세 응답에 `storages` 가 있다고 가정 | 상세 응답에 `storages` 없음 |

같은 것도 있다. 홈 목록이 오늘 날짜(`today`)와 식품 목록(`foods`)으로 이루어진다는 점, 식품에 `show_on_calendar` 가 들어 있다는 점, 날짜가 `YYYY-MM-DD` 글자라는 점, 다 먹음·버림 요청이 `{"status": "eaten"}` / `{"status": "discarded"}` 모양이라는 점, 주소가 `/api` 를 떼면 서로 일치한다는 점이다.

프론트엔드 점검 문서(`docs/FRONTEND-ERRORS.md`)의 "병합 시 확인"에도 입력 오류 모양이나 "기한 다시 적기" 응답이 임시 약속이라는 걱정이 적혀 있다. 이 차이를 실제로 맞춘 기록은 이 브랜치 안에서 찾지 못했다. 화면을 실제 서버에 연결해서 돌려 본 기록도 없다. **확인 필요**.
