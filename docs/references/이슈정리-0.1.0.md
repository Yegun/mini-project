### 문제 4: 상태 값 이름 (`4a5c926`, Yegun, 11-01 22:17)

- 원인: 화면이 서버와 합의하기 전에 임시로 지은 이름(`expiry_level`)을 썼다.
- 고친 방법: 화면의 이름과 값을 서버에 맞췄다. `expiry_level` → `expiry_status`, `relaxed/caution/urgent/expired` → `fresh/warning/soon/expired`.
- 고친 파일: `frontend/src/types/food.ts`, `types/foodDetail.ts`, `lib/statusColor.ts`, `components/FoodBarRow.tsx`, `FoodList.tsx`, `FoodSummary.tsx`, `mocks/foods.json`, `mocks/createdFoods.ts` (8개)
- 이슈 번호는 커밋에 적혀 있지 않다.

### 문제 5: 서버 오류 응답 읽기 (#21, `7727c4d`, 11-01 22:24)

- 원인: 화면이 `{ errors: { 칸이름: 안내 } }` 모양과 `200 + need_expiry` 를 가정했는데, 서버는 `{field, reason, message}` 와 `409 + expiry_required` 를 준다.
- 고친 방법: 서버 오류를 읽어 화면이 쓰는 결과로 바꾸는 파일을 새로 만들었다. 409 + `expiry_required` 면 "기한 다시 적기", 422 면 `field` 와 `message` 로 해당 입력칸 옆에 안내를 보인다(서버의 `expiry_date` 는 화면의 `expiry` 칸으로 연결). 그 밖은 일반 실패로 본다.
- 고친 파일: `frontend/src/api/errors.ts`(새 파일), `api/foodDetail.ts`, `api/foods.ts`

### 문제 6: DB 파일이 없을 때 (#22, `8de3630`, 11-01 22:42)

- 원인: DB 파일(`backend/data/fridge.db`, `rules.db`)은 사람이 `python -m app.db.init_db` 를 따로 실행해야 생겼다. 안 하면 서버가 켜져도 목록이 오류였다.
- 고친 방법: 서버가 켜질 때 `ensure_db()` 를 불러서 **없는 파일만** 만든다. 이미 있는 파일은 건드리지 않는다. 기존 `init_db` 는 규칙표를 지우고 다시 채우기 때문에, 식품 데이터와 개발자가 고친 규칙표를 지키려고 따로 나눴다(D-007).
- 고친 파일: `backend/app/main.py`, `backend/app/db/init_db.py`, `backend/app/db/README.md`, 시험 `backend/tests/test_ensure_db.py`(시험 4개: 둘 다 없으면 만든다, 있으면 건드리지 않는다, 없는 것만 만든다, 서버를 켜면 홈이 열린다)

### 문제 7: 등록 요청 칸 이름 (#23, `d2acacf`, 11-02 00:03)

- 원인: 화면이 규칙표 등록에 `rule_id` 를 보내고 직접 등록의 "며칠 뒤"를 `expiry_days` 로 보냈다. 서버는 모르는 칸이 있으면 오류(422)로 돌려주고, "며칠 뒤" 칸 이름은 `expiry_in_days` 다.
- 고친 방법: `rule_id` 를 없애고(이름으로 찾음), `expiry_days` 를 `expiry_in_days` 로 바꿨다. 직접 등록인지는 기한 칸(`expiry_date` 또는 `expiry_in_days`)이 있는지로 구분한다.
- 고친 파일: `frontend/src/types/register.ts`, `pages/RegisterPage.tsx`, `mocks/createdFoods.ts`

### 문제 8: 규칙표 검색 응답 (#24, `f3e73ab`, 11-02 00:20)

- 원인: 화면은 `id` 와 방법별 가능 여부(`storages`)를 기대했고, 서버는 쓸 수 없는 방법 목록(`not_allowed`)만 준다.
- 고친 방법: 서버 응답을 읽어 "상온·냉장·냉동 세 방법의 가능 여부"로 바꾸는 함수를 넣었다. 목록의 구분 값은 `id` 대신 이름(`name`)을 쓴다(규칙표 이름은 겹치지 않음, D-035).
- 고친 파일: `frontend/src/api/rules.ts`, `types/rule.ts`, `components/RuleSearch.tsx`

### 문제 9: 상세 화면의 불가 보관 방법 (#25, `bc7016d`, 11-02 01:15)

- 원인: 서버의 식품 상세 응답에 방법별 가능 여부(`storages`)가 없다. 화면은 이 값을 기대한다.
- 고친 방법: **서버는 그대로 두고 화면이 우회했다.** 상세를 불러온 뒤, 직접 등록 식품은 세 방법 모두 가능으로 보고, 규칙표 식품은 규칙표 검색(A2)에서 이름이 정확히 같은 항목의 "불가" 목록을 써서 채운다. 못 찾거나 검색이 실패하면 불러오기 실패로 본다.
- 고친 파일: `frontend/src/api/foodDetail.ts` (1개)

## 4. 처리 안 된 것은 왜 안 됐고, 처리 방법은 무엇인가

### 문제 9 후속: 서버 상세 응답에 방법별 가능 여부가 없음

- 왜 안 됐나: 검수에서 차이가 나왔을 때 사용자가 코드를 고치지 않고 차이로 남기기로 했다. 그 뒤 화면 쪽에서만 우회로 풀었고 서버는 바꾸지 않았다.
- 지금 영향: 화면은 정상으로 보이지만, 서버 응답과 화면이 기대하는 모양이 다른 채로 남아 있다.
- 처리 방법 후보
  1. **지금처럼 유지**: 화면이 규칙표 검색으로 채운다. 서버 변경이 없다.
  2. **서버 응답에 `storages` 추가**: `backend/app/view.py`, `backend/app/routers/foods.py` 에 넣고, 화면의 우회 코드(`frontend/src/api/foodDetail.ts`)를 지운다. 검수 기록에는 "화면은 이미 이 칸을 읽도록 만들어져 있다"고 적혀 있다.
- 필요한 결정: API-SPEC 의 A5(상세) 성공 응답에 방법별 가능 여부가 적혀 있는지 먼저 확인해야 한다. **확인 필요**

### 문제 10: 브라우저 뒤로가기

- 왜 안 됐나: 화면 전환을 주소가 아니라 상태값으로 하는 구조(`frontend/src/App.tsx` 주석에 의도라고 적힘)라서 생긴다. 고치려면 라우터 패키지 설치와 화면 구조 변경이 필요해 이번 범위를 넘는다고 보류했다(FRONTEND-ERRORS "다음 작업 후보").
- 영향: 상세나 등록 화면에서 뒤로가기를 누르면 앱이 끝난다.
- 처리 방법 후보
  1. 라우터 패키지를 설치해 화면마다 주소를 준다. **설치는 승인이 필요하다**(AGENTS.md).
  2. 패키지 없이 브라우저 기록(`pushState`, `popstate`)만 `App.tsx` 에서 다룬다. 범위가 작다.
- 필요한 결정: 1번과 2번 중 선택, 그리고 이번 버전에서 할지 다음 버전으로 미룰지.

### 문제 11: 규칙표 임시값

- 왜 안 됐나: 식품 이름 30개는 확정이지만 기본 보관 방법, 보관 가능 여부, 최대 보관 일수, 별칭은 식약처 기준으로 확인한 값이 아니라 개발용 임시값이다(D-036). 기준을 확인하는 일이 먼저다.
- 영향: 화면에 보이는 기한 숫자와 "불가" 보관 방법이 실제와 다를 수 있다.
- 처리 방법
  1. 식약처 기준으로 값을 확정한다(사람이 해야 하는 일).
  2. `backend/app/db/seed_rules.py` 의 값을 고치고 `python -m app.db.init_db` 로 규칙표를 다시 채운다.
  3. `python -m app.db.recalc_expiry --dry-run` 으로 바뀔 기한을 먼저 보고, `python -m app.db.recalc_expiry` 로 이미 등록된 규칙표 식품의 기한을 다시 계산한다.
  4. 화면의 가짜 규칙표(`frontend/src/mocks/rules.json`)는 가짜 데이터 모드에서만 쓰인다. 서버와 연결해 쓰는 동안에는 영향이 없다.

1. 원인을 확인한다 (파일과 커밋으로).

3. 고칠 파일을 정한다. 이슈 하나에 한 번에 한 가지만 고친다.
